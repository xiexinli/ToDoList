## 1 概念精讲（30 min）

**一句话定义**
Token 是模型读写文本的最小单位（可能是半个词、一个汉字或一个标点）；上下文窗口（context window）是一次请求里「输入 + 输出」合计能占用的 token 上限。

**它解决什么问题 / 为什么现在必须懂**
1. **计费按 token**：输入（prompt_tokens）与输出（completion_tokens）分开计价，输出通常更贵。你写的每一行 prompt 都是钱。
2. **窗口决定边界**：聊天历史、长文档、以后 RAG 召回的内容，全都要挤进同一个窗口；超了要么报错、要么被静默截断，效果莫名其妙变差。
3. **它是后面一切的地基**：W3 的文本切片本质是"按 token 切"；W4 的上下文压缩 / 记忆管理本质是"在窗口里做取舍"；第二个月做端侧模型时窗口更小，预算意识只会更重要。

**关键机制**（三条，按顺序理解）

① 文本 → token：分词器（tokenizer）把文本切成子词单元，再映射成数字 id。
```
"AI学习"  →  ["AI", "学", "习"]  →  [4821, 27183, 3310]   （示意，id 因模型而异）
```
高频词整体成 token，低频词被拆成碎片；标点、引号、数字往往各占一个 token——所以 JSON / 代码的"token 密度"比自然语言高。

② 一次请求的 token 账本（这是今天最该记住的一张图）：
```
┌──────────────── 上下文窗口（比如 32K tokens） ────────────────┐
│  系统提示  +  历史消息  +  本次输入  +  ⬅ 必须给输出留出空间  │
└──────────────────────────────────────────────────────────────┘
```
窗口大小随模型不同（以你所用模型的官方文档为准）。发请求前先算：`历史 + 输入 + 预期输出 ≤ 窗口`——不够就得截断、分块或压缩。

③ **服务端是无状态的**：每次请求彼此独立，模型不记得你上一轮说过什么。所谓"多轮对话"，是你的程序把历史消息重新拼进 messages 一起发过去。推论：**轮数越多，每次请求的 prompt_tokens 越大，成本随轮数持续上涨**。

**常见误区**
1. 很多人以为"字数 = token 数"。其实一个汉字常常约 0.7~1 个 token，而 JSON / 代码里的引号、括号、数字更密。同一段文字，不同模型的 tokenizer 结果也不同。**别背数字，学会测量**（今天的代码就是干这个）。
2. 很多人以为"窗口大就可以随便塞"。其实：a) 输出也要占窗口；b) 超长上下文的中间部分容易被忽略（俗称 lost in the middle）；c) 每次都发几万 token，延迟和成本都上去了。**窗口大 ≠ 应该塞满**。
3. 很多人以为"模型记得上一轮"。其实 API 是无状态的，历史是客户端每次重放的——这也解释了为什么很多聊天 App 关掉重开后"失忆"。

## 2 代码片段（40 min）

**场景**
给一段典型输入（商品文案 + 订单 JSON），先本地粗估 token 做超窗预判，再发真实请求，用接口返回的 usage 对照误差，最后亲手验证"服务端无状态"。

**依赖与版本**
零依赖——只用 Node.js 内置 fetch（Node 18+ 即可；本机实测 v26.7.0）。不需要 npm install 任何东西。

**最小可运行代码**（保存为 `token-budget-demo.mjs`）

```javascript
// token-budget-demo.mjs —— 零依赖，Node 18+ 直接跑：node token-budget-demo.mjs
// 作用：① 粗估 token 后再发请求；② 对照接口返回的真实 usage；③ 演示上下文预算与"无状态"
const BASE_URL = process.env.LLM_BASE_URL || 'https://api.openai.com/v1';
const API_KEY  = process.env.LLM_API_KEY;
const MODEL    = process.env.LLM_MODEL;
const CONTEXT_WINDOW = Number(process.env.LLM_CONTEXT_WINDOW || 32000); // 换成你所使用模型的实际窗口
const MAX_OUTPUT     = Number(process.env.LLM_MAX_OUTPUT || 1024);      // 给回复预留的输出预算

if (!API_KEY || !MODEL) { console.error('缺少 LLM_API_KEY / LLM_MODEL 环境变量'); process.exit(1); }

// ① 粗估函数：只用于发请求前心里有数，精确值永远以接口返回的 usage 为准
function roughTokens(text) {
  const cjk   = (text.match(/[一-鿿぀-ヿ]/g) || []).length;          // 中日韩字符
  const alnum = (text.match(/[A-Za-z0-9]/g) || []).length;              // 字母数字
  const punct = text.length - cjk - alnum - (text.match(/\s/g) || []).length; // 标点符号
  // 系数按本机端点实测校准（4 个样本平均误差约 8.5%）；换模型后可自行重标一次
  return Math.round(cjk * 0.75 + alnum / 5.5 + punct / 1.5) + 8;        // +8 ≈ 单条消息模板开销
}

async function chat(messages) {
  const res = await fetch(`${BASE_URL}/chat/completions`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${API_KEY}` },
    body: JSON.stringify({ model: MODEL, messages }),
  });
  if (!res.ok) throw new Error(`HTTP ${res.status}: ${(await res.text()).slice(0, 200)}`);
  return res.json();
}

// ② 一段典型的长文本：商品详情页文案 + 订单 JSON（Android/前端常见的输入形态）
const doc = `请用一句话总结下面内容。
【文案】${'轻量降噪耳机，40 小时续航，支持多设备连接，通勤与办公都合适。'.repeat(6)}
【数据】{"orderId":"20261029-XY7","items":[{"sku":"A-1001","qty":2,"price":19.9},{"sku":"B-2002","qty":1,"price":99.0}],"status":"paid"}`;

const est = roughTokens(doc);
console.log(`【估算】字符数=${doc.length}  粗估输入 token≈${est}`);
// 预算检查：输入 + 输出不能超过窗口
const usedPct = ((est + MAX_OUTPUT) / CONTEXT_WINDOW * 100).toFixed(1);
console.log(`【预算】窗口=${CONTEXT_WINDOW}  输入≈${est} + 输出上限=${MAX_OUTPUT}  占用≈${usedPct}%` +
            (est + MAX_OUTPUT > CONTEXT_WINDOW ? '  ⚠️ 超窗，必须截断或分块' : '  ✅ 未超窗'));

// ③ 真实 usage
const r1 = await chat([{ role: 'user', content: doc }]);
const u = r1.usage;
console.log(`【真实】prompt_tokens=${u.prompt_tokens}  completion_tokens=${u.completion_tokens}  total_tokens=${u.total_tokens}`);
if (u.prompt_tokens_details?.cached_tokens !== undefined)
  console.log(`【缓存】cached_tokens=${u.prompt_tokens_details.cached_tokens}（命中缓存的前缀不计全价）`);
console.log(`【偏差】估算 ${est} vs 实际 ${u.prompt_tokens} → 误差 ${(Math.abs(est - u.prompt_tokens) / u.prompt_tokens * 100).toFixed(0)}%`);
console.log(`【回复】${r1.choices[0].message.content.slice(0, 60)}...\n`);

// ④ 无状态验证：两个独立请求之间，服务端不会"记住"任何东西
await chat([{ role: 'user', content: '请记住这个订单号：20261029-XY7，只回复"好的"。' }]);
const r3 = await chat([{ role: 'user', content: '刚才我让你记住的订单号是多少？' }]);
console.log(`【无状态】第二次独立请求的回答：${r3.choices[0].message.content.slice(0, 80)}`);
console.log('→ 服务端不保存对话历史，历史必须由你的程序每次重新拼进 messages。');
```

**逐行要点**（只讲关键行）
- `roughTokens()`：三行分数别字/字母数字/标点三类分别估价。系数不是拍脑袋——是本机端点 4 个样本实测校准出来的（见"踩坑提示"）。换模型后应重新标定一次。
- `CONTEXT_WINDOW` / `MAX_OUTPUT` 两个常量：把"给输出留空间"变成代码里的显式预算，这是新手最容易漏的一笔账。
- `chat()`：OpenAI 兼容接口的四件套——`/chat/completions` 路径、`Authorization: Bearer` 头、JSON body（model + messages）、`res.ok` 判断。
- `u.prompt_tokens / completion_tokens / total_tokens`：**唯一可信的真值来源**。以后做成本估算、压缩历史、排查"为什么慢了贵了"，全从这里取证。
- 第 ④ 段两个独立请求：第二个"失忆"是设计使然，不是 bug——这就是"无状态"的现场证明。

**踩坑提示**（都是本机实测踩到的）
- 本机 DHwork 端点两个坑：① `max_tokens` 设成 `1` 会被拒绝（HTTP 400），给个正常值（如 64）就正常；② 它的 usage 里 **Anthropic 风格的 `cache_read_input_tokens` 与 OpenAI 风格的 `prompt_tokens_details.cached_tokens` 并存**——写通用代码前先打印一次完整 usage，别假设字段名固定。
- 估算公式永远只是估算：本机 4 个样本平均误差约 8.5%，单点可到 15%+（标点/数字越密偏差越大）。**用来预判量级，不用来做账**。
- 不同模型的 tokenizer 不同，中文压缩率差异明显；把公式迁移到新模型前，跑一遍今天的脚本重标系数。
- 别把窗口上限当成"配额"：塞满 = 更贵 + 更慢 + 中间内容被忽略。

**与我的工作结合**
- **Android**：做"AI 总结聊天记录 / 长文"功能时，先本地算 token 再决定截断点与分块策略；聊天类功能不要把全量历史每轮重放，用滑动窗口或"历史摘要"控制 prompt 体量——这是 App 里 AI 功能成本失控的第一大来源。
- **小程序 / 前端**：端上没有内置 tokenizer，用今天这个纯前端可复制的 `roughTokens()` 做预判——内容过长时先在 UI 上提示"已截断"或"分段处理"，比把 4 万 token 直接甩给后端、再随机超时报错体验好得多。
- **衔接后续**：今天这张"token 账本"就是 W4「Context Engineering（上下文工程）」的最小版本——腾讯那个岗位把"上下文压缩"写进职责，本质上是在做今天这件事的工业化版本。

## 5 明日预告与待复习（8 min）

- **明日主题**：消息结构（Roles）—— system / user / assistant / tool 四种角色各自的分工，以及"无状态"前提下如何亲手维护对话历史。
- **待复习（3 条）**
  1. Token ≠ 字数：中文约 0.7~1 token/字，JSON/代码更密；精确值以接口返回的 usage 为准。
  2. 窗口账本 = 系统提示 + 历史 + 输入 + 输出预留；超窗要截断/分块/压缩，不能硬塞。
  3. API 无状态：历史由客户端每次重放，轮数越多成本越高。
- **一句话复盘**：最容易忘的是——"窗口大"和"该塞满"完全是两回事，输出也要占预算。
