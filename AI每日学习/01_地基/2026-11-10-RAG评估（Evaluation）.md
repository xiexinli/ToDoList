## 1 概念精讲（30 min）

**一句话定义**
RAG 评估 = 用**固定的测试集 + 明确的指标**，"分层"度量 RAG 质量：**检索层**量"找得对不对"（Hit@k / MRR / nDCG），**生成层**量"说得对不对"（忠实度 Faithfulness / 答案相关性 Relevance）；每次改动后重跑同一套测试集——**用数字对比，而不是凭感觉**。

> 一句话记住本质：**评估不是"打分"，是"对比"**——没有基线（baseline），就没有评估。

**它解决什么问题 / 为什么现在必须懂**
1. **RAG 的旋钮太多**：切片大小、embedding 模型、top_k、加不加重排、prompt 措辞——每一个都"感觉能变好"，**没有评估就是拍脑袋调参**。
2. **"改好一个、改坏三个"是常态**：本讲实测里，加重排在第二轮测试集上把 **MRR 从 0.90 拉到 0.83**——**不量数字，你根本不知道自己在帮倒忙**。
3. **线上出问题时要能定位"哪一层坏了"**：是检索没捞到（召回问题），还是捞到了但答错（生成问题）？——**不分层评估，就只会瞎猜**。

**关键机制：分层 + 对比**

```
① 被测系统                                       ② 指标分层
用户问题 ──► [检索层] ──► 片段 ──► [生成层] ──► 答案
                │                        │
        量"找得对不对"              量"说得对不对"
        Hit@k / MRR / nDCG          忠实度 Faithfulness
        Recall@k                    答案相关性 Relevance
                └───────────┬────────────┘
                            ▼
                ③ 固定测试集 → 每次改动重跑 → 对比
                 （改旋钮 → 量指标 → 保留 or 回滚）
```

- **Hit@k（命中率）**：前 k 条结果里**有没有**金标文档；每题只有 1 或 0，全测试集取平均。看的是"**覆盖面**"。
- **MRR（平均倒数排名）**：金标排第 1 名得 1 分、第 2 名 0.5 分、第 3 名 0.33 分，没命中 0 分，再取平均。看的是"**排序质量**"——正确的排得越靠前越好。
  两者要**配对看**：Hit@3=1.0 但 MRR=0.33 意味着"全都能找到、但都排在第三名"（喂给 LLM 的上下文里噪音多）。
- **忠实度（Faithfulness）**：答案内容是否**全部**能被检索片段支持——本质就是 11-09 讲的"引用校验"，只是这里作为**离线指标**批量跑。
- **答案相关性（Relevance）**：答案是否真的**回答了**用户的问题——"忠实但跑题"同样不及格（实测里有活例子）。
- **测试集从哪来**：① 拿知识库文档"倒着出题"（今天用的办法）；② 线上真实用户问题；③ badcase 沉淀。**20~50 条就能开始迭代**，不必等"几千条标注"。

**评估的三类"裁判"**（生成层打分靠谁）：
| 打分者 | 成本 | 可靠性 | 适合 |
|---|---|---|---|
| 人工标注 | 最贵 | 金标准 | 校准其他裁判、抽检 |
| LLM-as-Judge | 便宜 | 有系统偏差（位置/长度/自我偏好） | A/B 相对比较 |
| 专用小模型（如 HHEM） | 居中 | 稳定但窄 | 上线后的持续监控 |

**常见误区**
1. **"评估要先有几千条人工标注才能开始。"** ✗ 20~50 条真实问题就能起步，边跑边补；今天实测用的就是 **12 条文档 + 10 个问题**。
2. **"看总分就行。"** ✗ 要**分层 + 逐条 diff**。今天两轮总分都 0.90（看着不错），但逐条看，**唯一的失败题都是同一类：金标连 top5 都没进——召回失败**。评估帮你把结论从"还行"推进到"**该上混合检索（BM25），而不是继续调重排**"。
3. **"加了个优化，指标一定会变好。"** ✗ 实测反例：重排在第二轮把 **MRR 0.90 → 0.83**。**"加了重排"和"变好了"之间没有必然关系，只有评估能告诉你是不是真的**。
4. **"LLM 裁判的分数是绝对真理。"** ✗ 今天实测：同一输入连跑 6 次，faithful 出现 1 次相反判定，relevant 在 **2~5 分**之间乱跳（rubric 对"拒答"这类边界没写死）。**裁判只做相对比较、必须配人工抽检、rubric 要写死边界情况**。

## 2 代码片段（40 min）

- **场景**：一个**小型 RAG 评估器**。被测系统 = 12 条知识库文档 + 检索（可切换"纯向量"和"向量+重排"两种配置）。用**两套测试集**（同一批问题的"文档措辞版"和"用户口吻版"）量出 **Hit@3 / MRR**；再用 **LLM 裁判**对生成层量**忠实度 / 相关性**。**这就是"改配置 → 量指标 → 对比 → 得结论"的完整闭环。**
- **依赖与版本**：只用 Python 标准库（`urllib / json / math`），**无需任何 pip 安装**。模型全部走本机 DHwork OpenAI 兼容端点：`bge-m3`（embedding）、`bge-reranker-v2-m3`（rerank）、`deepseek-v4-flash-dhwork`（生成 + 裁判，`temperature=0`）。本机 python3 = 3.9.6。

**完整代码 `rag_eval.py`**（约 110 行，已在 macOS + python3.9 实跑）

```python
# -*- coding: utf-8 -*-
# rag_eval.py —— 给 RAG 装一份「成绩单」：检索层 Hit@k / MRR + 生成层忠实度判定
# 依赖：仅标准库（urllib / json / math）。模型走本机 DHwork OpenAI 兼容端点。
import base64, json, math, os, urllib.parse, urllib.request

# ---------- 0. 连接本机端点（令牌位置同前几讲） ----------
p = os.path.expanduser("~/Library/Application Support/DHwork/config/aionui-config.txt")
d = json.loads(urllib.parse.unquote(base64.b64decode(open(p).read().strip()).decode()))
TOK = d["desktop.bootstrapAuth"]["dhwork"]["accessToken"]
BASE = "https://www.dhcoder.net/llm-api/v1"
HEAD = {"Authorization": "Bearer " + TOK, "Content-Type": "application/json"}

def api(path, payload):
    req = urllib.request.Request(BASE + path, data=json.dumps(payload).encode(), headers=HEAD)
    return json.load(urllib.request.urlopen(req, timeout=180))

# ---------- 1. 被测系统：12 条知识库文档 + 两轮测试集 ----------
DOCS = {
"d01": "重排（Rerank）使用交叉编码器把查询与候选片段逐对联合编码打分，精度显著高于向量相似度，但对『候选数×查询数』的逐对推理意味着延迟与成本更高，通常只用于对前 20~100 条候选做精排。",
"d02": "切片（Chunking）过大时，一个块的向量会被多个主题平均，语义变模糊，检索时难以精确命中；过小则容易丢失上下文。常见折中是 300~800 token 并保留 10%~20% 重叠。",
"d03": "HNSW 是一种近似最近邻（ANN）索引：在向量之间构建多层图结构，查询时从稀疏的顶层向稠密底层贪心跳转，用少量召回损失换取数量级的速度提升，是向量数据库的常用默认索引。",
"d04": "BM25 是稀疏关键词检索的经典算法，依据词频与逆文档频率打分。它对专有名词、产品型号、错误码等精确字符串命中率很高，但对同义改写无能为力，常与向量检索互补使用。",
"d05": "混合检索（Hybrid Search）同时跑 BM25 与向量两路召回，再用 RRF（Reciprocal Rank Fusion，倒数排名融合）把两组排名合并：RRF 只看名次不看分数，避免两类分数不可比的问题。",
"d06": "引用与防幻觉：要求答案中每句陈述都标注其依据的片段编号，输出前逐句校验『该陈述是否能被其引用片段直接支持』，不支持的句子标注为无依据或触发重生成。",
"d07": "上下文窗口（Context Window）是模型单次请求能处理的 token 上限，包含提示词、检索片段、历史对话与输出。超出上限时需要截断、摘要或裁剪检索片段数量。",
"d08": "流式输出（Streaming）通过 SSE 逐 token 推送，把『首字延迟』从整段生成时间降到亚秒级；移动端常配合打字机效果缓解等待焦虑。",
"d09": "temperature 越低输出越确定，适合抽取、判定类任务；越高越发散，适合头脑风暴与文案创作。评估与判定类任务通常固定 temperature=0 以保证可复现。",
"d10": "Hit@k 衡量前 k 条检索结果里是否包含正确文档（命中率）；MRR 用第一条命中名次的倒数衡量『正确结果排得多靠前』。两者配对使用时既能看覆盖面，也能看排序质量。",

]

IDS = list(DOCS)
def embed(texts):
    r = api("/embeddings", {"model": "bge-m3", "input": texts})
    return [x["embedding"] for x in r["data"]]

def cos(a, b):
    return sum(x*y for x, y in zip(a, b)) / math.sqrt(sum(x*x for x in a) * sum(x*x for x in b))

DOCV = embed([DOCS[i] for i in IDS])          # 文档向量只算一次，全流程复用

# ---------- 2. 两种待对比的检索配置 ----------
def search_vector(qv, k=3):                    # 配置A：纯向量 top3
    ranked = sorted(((cos(qv, v), i) for v, i in zip(DOCV, IDS)), key=lambda x: -x[0])
    return [i for _, i in ranked[:k]]

def search_rerank(q, qv, k=3):                 # 配置B：向量 top5 → rerank → top3
    cand = search_vector(qv, 5)
    r = api("/rerank", {"model": "bge-reranker-v2-m3", "query": q,
                        "documents": [DOCS[i] for i in cand]})
    # results[].index 指向输入下标，按它对齐再做降序
    scored = sorted(((x["relevance_score"], cand[x["index"]]) for x in r["results"]), key=lambda x: -x[0])
    return [i for _, i in scored[:k]]

# ---------- 3. 指标：Hit@k 看覆盖面，MRR 看排序质量 ----------
def hit_at_k(ranked, gold, k=3):
    return 1.0 if gold in ranked[:k] else 0.0

def mrr(ranked, gold):
    return 1.0 / (ranked.index(gold) + 1) if gold in ranked else 0.0

def evaluate(name, T):                         # 统一跑『一个测试集 × 两种配置』
    qv = embed([q for q, _ in T])
    ha = ma = hb = mb = 0.0
    for i, (q, gold) in enumerate(T):
        ra, rb = search_vector(qv[i]), search_rerank(q, qv[i])
        ha += hit_at_k(ra, gold); ma += mrr(ra, gold)
        hb += hit_at_k(rb, gold); mb += mrr(rb, gold)
        print("  %s%s  %s | 重排top3=%s" % ("✓" if gold in ra else "✗",
              "✓" if gold in rb else "✗", q, rb))
    n = len(T)
    print("  [%s] 纯向量 Hit@3=%.2f MRR=%.2f ｜ 向量+重排 Hit@3=%.2f MRR=%.2f\n" % (name, ha/n, ma/n, hb/n, mb/n))

# ---------- 4. 生成层：忠实度（Faithfulness）+ 相关性（Relevance） ----------
GEN_SYS = ("你是客服知识助手。只依据提供的资料片段回答问题，不得引入片段之外的信息；"
           "资料没提到就回答『资料中未提及』。回答尽量简短。")
JUDGE_SYS = ("你是 RAG 答案质检员。给定【问题】【资料片段】【候选答案】，输出 JSON："
             '{"faithful":true/false, "relevant":1-5, "reason":"≤20字"}。'
             "faithful=true 仅当答案全部内容都能被资料片段直接支持；答案含片段之外的信息（即使正确）"
             "或未按资料拒答，都判 false。relevant 衡量答案是否解决了问题。只输出 JSON。")

def chat(sys_prompt, user_prompt):
    r = api("/chat/completions", {"model": "deepseek-v4-flash-dhwork", "temperature": 0,
                                  "messages": [{"role": "system", "content": sys_prompt},
                                               {"role": "user", "content": user_prompt}]})
    return r["choices"][0]["message"]["content"].strip()

def gen_and_judge(q, doc_ids):
    ctx = "\n".join("[%s] %s" % (i, DOCS[i]) for i in doc_ids)
    ans = chat(GEN_SYS, "资料片段：\n%s\n\n问题：%s" % (ctx, q))
    verdict = chat(JUDGE_SYS, "【问题】%s\n【资料片段】\n%s\n【候选答案】%s" % (q, ctx, ans))
    return ans, verdict

if __name__ == "__main__":
    print("== 测试集①：措辞贴着文档 ==")
    evaluate("文档措辞", TESTS_DOC)
    print("== 测试集②：真实用户口吻 ==")
    evaluate("用户口吻", TESTS_USER)
    print("== 生成层：忠实度 + 相关性（3 个刻意选的案例）==")
    CASES = [
      ("为什么我们的重排服务比向量那一层慢很多？", ["d01", "d02", "d05"]),   # 检索命中
      ("老板要我拿数字说话：加重排到底值不值？", ["d01", "d11", "d02"]),     # 检索失败（金标 d12 没进）
      ("公司的年假政策是多少天？", ["d01", "d02"]),                          # 超纲问题（语料里没有）
    ]
    for q, ids_ in CASES:
        ans, verdict = gen_and_judge(q, ids_)
        print("  问题: %s\n  答案: %s\n  裁判: %s\n" % (q, ans, verdict))
```

```
  ✓✓  怎么衡量正确答案是不是排在第一个？ | 重排top3=['d10', 'd12', 'd01']
  [用户口吻] 纯向量 Hit@3=0.90 MRR=0.90 ｜ 向量+重排 Hit@3=0.90 MRR=0.83

== 生成层：忠实度 + 相关性（3 个刻意选的案例）==
  问题: 为什么我们的重排服务比向量那一层慢很多？
  答案: 因为重排需对“候选数×查询数”逐对联合编码打分，延迟与成本远高于向量相似度计算。
  裁判: {"faithful": true, "relevant": 5, "reason": "准确引用片段解释重排慢原因"}

  问题: 老板要我拿数字说话：加重排到底值不值？
  答案: 资料仅说明：重排精度显著高于向量相似度，但延迟和成本更高，通常只用于对前 20~100 条候选做精排。是否“值”需结合你的候选数、查询量和成本预算判断，具体收益数字资料未提及。
  裁判: {"faithful":true,"relevant":4,"reason":"忠实反映资料，指出需结合具体情况，但未给出明确数值结论。"}

  问题: 公司的年假政策是多少天？
  答案: 资料中未提及。
  裁判: {"faithful": false, "relevant": 1, "reason": "资料未提及年假政策"}

```

**三处值得停下来想一秒的地方**
1. **两轮里重排都没让 Hit@3 变好，第二轮还把 MRR 拉低了**（0.90→0.83：rerank 把"随机性那题"的金标从第 1 名压到第 3 名）。→ **"加了优化"≠"变好了"**。评估的第一个作用，就是把无效/负向优化拦在门外。
2. **两轮唯一的失败题都是同一类：金标 d12 连 top5 都没进**——rerank 只能在已召回候选里重排，**召回失败它救不了**。→ 评估把结论从"某题答不对"推进到了"**该修召回层（上混合检索/BM25），别继续折腾重排**"——这就是"分层"的回报。
3. **超纲问题的裁判连跑 6 次：faithful 5 次 true、1 次 false；relevant 在 2~5 分之间乱跳**。→ **LLM 裁判不是真理机器**：rubric 必须把边界情况写死（"拒答是否算 faithful"），并且永远配人工抽检。

- **逐行要点**
  - `DOCV = embed(...)` 文档向量只算一次、全流程复用——评估脚本要反复复跑，**别每次都重新嵌入知识库**。
  - `search_rerank` 里用 **`x["index"]` 对齐**候选（rerank 响应自带 index 字段，不要假设 results 顺序与输入一致）。
  - `hit_at_k` 与 `mrr` 是**纯函数**：与检索引擎解耦，换任何 RAG 实现都能复用——**评估代码要独立于被测代码**。
  - `temperature: 0` 用于生成与裁判：判定任务关掉随机性（11-05 / 11-09 讲过）。
  - 生成侧喂的是**检索的产物**（top3 片段）：所以"检索失败"会顺着链路传导到生成侧——案例 2 里模型只能说"资料未提及"，**忠实但无用**（relevant 掉到 4）。
- **踩坑提示**
  1. **测试集设计比脚本本身难**：今天两轮测试集里，多数题目"措辞贴着文档"，Hit@3 天然 0.90——**区分度不够**。生产上要写"真实用户会怎么问"（第二轮的方向），还要刻意加**难例**（同主题多文档竞争、口语化、含错别字）。
  2. **别让测试集泄进 prompt**：金标的问题和答案一旦被写进系统提示词，指标会虚高——**评估集要像考试卷一样保密**。
  3. **单题名次会抖动**：复跑时个别问题的 top3 顺序可能轻微变化（本次复跑中第 2、3 名的互换出现过）。**看总体指标趋势，别盯单题名次**；需要完全复现就把文档向量持久化。
  4. **裁判 rubric 要写死边界**：把"拒答算不算 faithful""答案比资料更啰嗦算不算"这些写进 rubric，否则裁判每次理解都不一样（今天实测 relevant 2~5 乱跳）。
  5. **成本**：每次全量评估 = 问题数 ×（1 次嵌入 + 1 次检索(+1 次 rerank) + 1 次生成 + 1 次裁判）。本讲脚本 30 题级评估 25 秒跑完——**评估本身也是要花钱的，纳入开发预算**。
