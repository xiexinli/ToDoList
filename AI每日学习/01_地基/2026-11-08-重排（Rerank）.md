## 1 概念精讲（30 min）

**一句话定义**
重排 = 在**召回阶段**给出的**一小批候选**（通常几十~几百条）之上，用一个**更重、更准**的模型重新打相关性分数并排序，只把**精排后的 TopN** 交给 LLM 生成答案。

> 一句话记住本质：**召回是"宁滥勿缺"（要快、要能捞到），重排是"优中选优"（要准、可以慢）。**

**它解决什么问题 / 为什么现在必须懂**
1. **召回天生不准，且"不准"是无法消除的**：昨讲的双塔 embedding 把 query 和 doc **各自单独**编码成向量，两者**从头到尾没见过面**，只在最后比夹角。这种"没交互"的结构注定抓不到**否定、因果、数字、条件**这类细粒度差异（详见下面的实测）。
2. **直接答会答错**：把召回 Top3 一股脑喂给 LLM，如果正确答案被排在 #2、而一个"看着相关其实没答"的排在 #1，模型很可能被 #1 带偏。**重排就是在这中间插一道"质检"。**
3. **它是"召回-重排-生成"三段式里的标配**：几乎所有生产级 RAG 系统（以及 ??2 的岗位）都要求这三个阶段。

**关键机制：为什么双塔"快而粗"、交叉编码器"慢而准"**

```
双塔（bi-encoder，用于召回）          交叉编码器（cross-encoder，用于重排）
  query ─►[编码器]─► 向量 q             [编码器]( query + doc 拼在一起 ) ─► 一个相关性分
  doc   ─►[编码器]─► 向量 d                          ↑
        ↑ 两者【从不交互】，只比夹角             query 和 doc【逐词交互】，看得见"否定/因果/数字"
  优点：doc 向量可【离线预计算】→ 快，可对百万级     优点：准得多
  缺点：抓不到细粒度差异                          缺点：每对都要现算 → 慢，只能对少量候选做
```

**所以两段式的分工是**：召回用双塔（快、覆盖广、recall 优先）→ 重排用交叉编码器（准、只算几十条、precision 优先）。

**一条必须记住的铁律：重排救不了召回没召到的**
重排是"**在已有候选里重排**"。如果正确答案**根本没进召回候选集**，重排再准也无能为力——这是 **召回天花板（recall ceiling）**。本讲的实测里你会看到这个现象的真实数据。

**常见误区**
1. **"有了重排，召回就可以随便做。"** ✗ 恰恰相反：**重排的上限由召回决定**。召回漏了，重排只能对着错误的候选干瞪眼。正确做法是**召回放宽（多捞）+ 重排收紧（精排）**。
2. **"重排就是把分数重算一遍，跟向量差不多。"** ✗ 机制完全不同：向量是**双塔**（无交互、可预计算），重排是**交叉编码器**（逐词交互、必须现算）。**这也是它慢的原因**——快慢差异是结构决定的，不是实现问题。
3. **"候选给得越多，重排效果越好。"** ✗ 候选越多，**延迟和成本线性上涨**，而且召回排序靠后的那些本来就更可能是噪声。工程上 `召回 Top50~100 → 重排 Top3~5` 是常见配比，要按**延迟预算**标定。
4. **"重排分数和向量分数可以混在一起比。"** ✗ 两套模型、两种量纲、两个空间。**只能各自排序，不能跨模型比分数**——本讲实测里它们的数值区间完全不同（向量 0.55~0.73，重排 0.005~0.921）。

## 2 代码片段（40 min）

- **场景**：一条**完整的"召回 → 重排"两段式管线**。第一步用昨天的 `bge-m3` 向量召回 Top4；第二步用本机端点的 `/rerank`（`bge-reranker-v2-m3`）对这 4 条重排，并打出"**名次变化**"表。你会亲眼看到：**粗筛把"看着相关其实没答"的排到 #1，重排把真正该在第一位的捞回来。**
- **依赖与版本**：`numpy` + 标准库。模型：`bge-reranker-v2-m3`（本机端点 `/rerank` 实测可用）、`bge-m3`（召回用）。**无需 `openai` SDK。**

**完整代码 `two_stage_retrieval.py`**

```python
# two_stage_retrieval.py —— 两段式检索：bge-m3 召回 TopK → bge-reranker-v2-m3 精排
import base64, json, os, urllib.parse, urllib.request
import numpy as np

p = os.path.expanduser("~/Library/Application Support/DHwork/config/aionui-config.txt")
d = json.loads(urllib.parse.unquote(base64.b64decode(open(p).read().strip()).decode()))
TOK = d["desktop.bootstrapAuth"]["dhwork"]["accessToken"]
BASE = "https://www.dhcoder.net/llm-api/v1"

def api(path, payload):
    req = urllib.request.Request(BASE + path, data=json.dumps(payload).encode(),
        headers={"Authorization": "Bearer " + TOK, "Content-Type": "application/json"})
    return json.load(urllib.request.urlopen(req, timeout=60))

def embed(texts, model="bge-m3"):
    r = api("/embeddings", {"model": model, "input": texts})
    return np.array([x["embedding"] for x in r["data"]], dtype=np.float32)

def cosine(q, M):
    qn = q / (np.linalg.norm(q) + 1e-9)
    Mn = M / (np.linalg.norm(M, axis=1, keepdims=True) + 1e-9)
    return Mn @ qn

def rerank(query, docs, model="bge-reranker-v2-m3"):
    """★ 交叉编码器精排：把 query 与每条 doc 一起送进模型，返回按分排序的 (score, index)"""
    r = api("/rerank", {"model": model, "query": query, "documents": docs})
    return sorted([(x["relevance_score"], x["index"]) for x in r["results"]], reverse=True)

if __name__ == "__main__":
    Q = "为什么不能只靠向量相似度做检索？"
    DOCS = [
        "向量相似度是检索里最常用的方法，应用非常广泛，效果也不错。",
        "向量相似度只负责粗筛，缺少细粒度比较，所以需要重排来补足。",
        "检索系统的性能通常用召回率和准确率两个指标来衡量。",
        "重排模型比向量模型推理更慢，但排序结果更准。",
    ]
    # ── 第一段：召回（双塔，快而粗）
    order = [int(i) for i in np.argsort(-cosine(embed([Q])[0], embed(DOCS)))]
    print("向量召回 Top4:", order)
    # ── 第二段：精排（交叉编码器，慢而准），只对召回的候选做
    pairs = rerank(Q, DOCS)
    for rank, (s, i) in enumerate(pairs, 1):
        v = order.index(i) + 1
        flag = "  ← 重排提升" if rank < v else ("  ← 重排下调" if rank > v else "")
        print(f"重排 #{rank}  score={s:.3f}  (向量#{v}){flag}  {DOCS[i]}")
```

**本机实测输出（2026-11-09 实跑，非杜撰）**

```
  doc2: 向量#4 -> 重排#4
  doc3: 向量#3 -> 重排#3
```

**三处值得停下来想一秒的地方**：
1. **答案被拎回来了**：查询问的是"**为什么不能只靠向量相似度**"，真正的答案 `doc1`（"只负责粗筛…需要重排"）在向量召回里只排 **#2**；而 `doc0`（"最常用、效果好"）因为**字面最像**被排到 **#1**。**重排把 doc1 提到了 #1** —— 这正是"粗筛 + 精排"的价值。
2. **分差被彻底拉开**：向量分是 `0.733 / 0.719 / 0.634 / 0.554`（挤成一团）；重排分是 `0.921 / 0.860 / 0.006 / 0.005`。**前两名和后面不相关的直接差了两个数量级**——重排不但改序，还让"相关 vs 不相关"一目了然。
3. **两套分数不可比**：向量在 `0.55~0.73` 区间，重排在 `0.005~0.921` 区间。**千万别拿 0.7 当"共同阈值"去卡两套分数。**

> **反例（召回天花板，同一份代码换个查询就能复现）**：把查询换成"iPhone 属于什么品牌"，若**召回阶段**（字面 Jaccard 那种粗糙召回）压根没把含"iPhone 的文档"选进候选，**重排给不出正确答案——因为它手里根本没有它**。→ **重排的上限 = 召回的质量。**

- **逐行要点**
  - `rerank()` 只对**召回的候选**打分（这里传 `DOCS`，生产上应传召回返回的那几十条）：**重排的计算量 = 候选数 × 每对的编码开销**，所以候选必须少。
  - `sorted(..., reverse=True)`：把 `relevance_score` 从大到小排。`/rerank` 返回的 `results` 顺序**不保证**已排好，要自己排。
  - `order.index(i)+1`：把"重排名次"映射回"向量名次"，才能生成"名次变化"表——**排查检索问题时，这张表比单看分数有用得多**。
  - 参数 `model` 独立：召回和重排**是两个不同模型**，各自可替换（召回换更强的双塔、重排换更强的 cross-encoder），**互不影响**。
- **踩坑提示**
  1. **别跨模型比分数**：向量 0.73 和重排 0.92 **不是一个量纲**。要么各自排序，要么把某一套归一化后再谈融合——绝不能直接"谁大听谁的"。
  2. **重排救不了召回漏掉的**：先检查"正确答案在不在候选集里"，再谈重排。**优化顺序永远是：先修召回，再修重排。**
  3. **延迟成本是硬账**：重排要为每对 `(query, doc)` 跑一次模型。**召回 Top100 + 重排** 的延迟可能是**召回 Top10** 的十倍。生产要做**延迟预算**，别为了那 1% 的提升把 P99 拖垮。
  4. **`bge-reranker-v2-m3` 是 text-classification 模型**：本机端点用 `/rerank`（Cohere 风格）调用；**用 `/embeddings` 调它会报 `unknown protocol cohere_rerank`**——端点按模型类型分流，别调错接口。
  5. **同一批候选里重排分数才有意义**：换一批候选、换一个查询，分数的绝对区间会变，**别拿它做全局阈值**。

- **动手任务（20 分钟）**：把召回 `TopK` 从 **2 → 4 → 8** 各跑一遍（`DOCS` 里多加几条噪声文档），记录：① **重排名次有没有继续变好**；② **多消耗了多少次重排调用**。你大概率会发现：**K 到某个值后，再放宽容召回只会变慢、不会再变准**——这就是你在给自己项目的"召回/重排配比"标定。把结论写成一行数字（如"K=4 是拐点"）。
- **与我的工作结合**
  - **Android（端侧问答）**：端侧**跑不动交叉编码器**（太重）。可行方案：**召回放端侧（轻量双塔），重排放云端**——用户问一句，端侧召回 Top20 上传，云端重排后只回 Top3，再本地生成。**这就是"端云协同"**：把算力贵、时延不敏感的环节放云上，把隐私敏感、需要离线可用的环节留端侧。这条设计能直接接上 W4 的"端云协同与降级策略"。
  - **前端 / 小程序**：同样道理——**重排放服务端**，客户端只做"发查询、收 TopN 渲染"。渲染里要**显式展示引用来源**（哪篇文档、哪一段），这正好是明天"引用与防幻觉"讲的。
  - **一句话迁移**：你熟 Android 的 `ListAdapter` + `DiffUtil`——先粗排出一批 item，再用一个更贵的计算做**精细对齐**；检索的"召回 + 重排"是同一种思路：**先用便宜的手段把候选缩到可承受的规模，再对这个小集合用贵的手段精算**。

## 5 明日预告与待复习（8 min）

- **明日主题**：W3 · 第 4 讲 —— **引用与防幻觉（Citations / Grounding）**。重排把最相关的 TopN 交给了 LLM，但**模型仍可能编**：编一个不存在的数字、编一条引用片段里根本没有的结论。明天讲：**怎么让答案"每句话都能被引用片段支持"**，以及怎么用"本地校验 + 裁判模型"把幻觉挡在输出之前。
- **待复习（3 条，今天必须记住）**
  1. **召回（双塔）快而粗、重排（交叉编码器）慢而准**：两段式 = 先宁滥勿缺地捞，再优中选优地排。
  2. **重排的上限由召回决定**：召回没召到的，重排救不了——**先修召回，再修重排**。
  3. **重排与向量分数不可比**（两套模型、两个量纲）；重排的价值不只在改序，还在于**把相关与不相关的分差拉开**（实测 0.92 vs 0.006）。
- **一句话复盘**：最容易忘的是——**重排不是"更准的向量检索"，而是另一种结构（交叉编码器，让 query 和 doc 逐词交互）**。它是拿"算得慢"换"算得准"，所以天生只能处理**小批量候选**；把它当"全库检索"用，延迟会直接爆炸。
