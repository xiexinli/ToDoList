## 1 概念精讲（30 min）

**一句话定义**
Embedding（向量化）= 把一段文本映射成一个**固定长度的稠密向量**（本机实测 `bge-m3` 是 **1024 维**），使得**语义相近的文本，向量方向也相近**。向量检索 = 在向量空间里找方向最接近查询的 **TopK** 个 chunk。

> 一句话记住本质：**它把"意思像不像"变成了一道几何题——比较两个向量的夹角。**

**它解决什么问题 / 为什么现在必须懂**
1. **关键词检索的死角**：BM25 / 关键词只能匹配"**字面相同**"。你问"怎么让检索结果更准"，而文档里写的是"重排能提升检索精度"——**没有一个字一样，但意思是同一件事**，关键词检索命中不了，向量检索能。
2. **它是 W3 后三讲的地基**：切片（上周）是"切出单位"，向量化（今天）是"让单位可比"，重排（明天）是"把召回结果排得更准"，引用与防幻觉（后天）是"让答案能被核对"。**没有今天的向量，后面全是空中楼阁。**
3. **它是招人要求里的高频词**：本讲的岗位观察里，"向量索引算法（LSH、IVF、HNSW）"直接写在职责第一条。

**关键机制：向量检索在链路里的位置**

```
 离线（入库）                            在线（提问）
 chunk₁ ─┐                            用户问题
 chunk₂ ─┼─► Embedding 模型 ─► 向量库    │
 chunk₃ ─┘   （bge-m3, 1024维）          ▼
        ▲                            Embedding（同一个模型！）
        └── 11-06 切片产出                    │
                                             ▼
                          余弦相似度 ─► 排序 ─► TopK 命中 chunk
                                              （今天讲这里；明天用重排把 TopK 再精排）
```

**三个必须刻进脑子里的点**
- **同一个模型**：入库用哪个 embedding 模型，查询时必须用**同一个**。换模型 = 旧向量全部作废，必须全量重算 + 重建索引。
- **余弦相似度**：`cos(A,B) = (A·B) / (|A|·|B|)`，取值 `[-1, 1]`，越接近 1 越像。它只看向量**夹角**，不看长度——所以向量长度不影响结果。
- **ANN 索引**：几百万条向量不可能每条都算一遍（暴力检索 O(N)）。生产库用 **HNSW / IVF / LSH** 做**近似最近邻（ANN）**，用一点点召回损失换几十上百倍的速度。

**常见误区**
1. **"向量检索是关键词检索的升级版，一定更好。"** ✗ 两者互补。**精确串（型号 `iPhone 17 Pro`、订单号、人名、错误码）关键词更强**；**语义问题（"怎么更准" vs "提升精度"）向量更强**。生产上常用**混合检索（hybrid）**：两路各取 TopK 再融合。本讲末尾的动手任务就是让你亲手看到两者的差别。
2. **"相似度分数可以当固定阈值卡。"** ✗ **分数只在"同一查询、同一模型的这一批候选"内部相对可比**，跨查询/跨模型绝对值不可比。本机实测同一查询里 `0.62 / 0.60 / 0.58` 有区分度，但不能说"0.6 以上才相关"——换个查询分布就变。
3. **"维度越高越好。"** ✗ 维度是**模型选择的结果**（本机 `bge-m3`=1024 维、`text-embedding-3-small`=1536 维），不是可调参数。维度越大，存储与检索算力线性上涨，**而准确率不一定涨**。
4. **"入库的 chunk 和查询可以分别用不同模型。"** ✗ 向量空间不通用，不同模型的向量**根本不在同一个空间里**，算出来的相似度是垃圾。

## 2 代码片段（40 min）

- **场景**：一个**真实调用本机 embedding 端点**的最小向量检索器。它把一组文档向量化 → 把查询向量化 → 用余弦相似度算 TopK → 同时跑一个"关键词朴素基线"做对照，让你亲眼看到**语义检索赢在哪里**。可直接改造成你项目里的检索层。
- **依赖与版本**：`numpy`（本机已装，1.x 均可）+ 标准库 `urllib / json / base64`。**不需要 `openai` SDK（本机未安装）**。模型：`bge-m3`（1024 维，本机端点实测可用）。鉴权令牌取自 `~/Library/Application Support/DHwork/config/aionui-config.txt`。

**完整代码 `vector_search.py`**

```python
# vector_search.py —— 真实调用 DHwork 端点的 /embeddings，做余弦相似度 TopK 检索
# 依赖：numpy + 标准库（无需 openai SDK）。Python 3.9+ 可跑。
import base64, json, os, urllib.parse, urllib.request
import numpy as np

# ── 0. 从本机配置里取端点令牌（DHwork 客户端登录态）
p = os.path.expanduser("~/Library/Application Support/DHwork/config/aionui-config.txt")
d = json.loads(urllib.parse.unquote(base64.b64decode(open(p).read().strip()).decode()))
TOK = d["desktop.bootstrapAuth"]["dhwork"]["accessToken"]      # ★ 扁平点号键，不是嵌套
BASE = "https://www.dhcoder.net/llm-api/v1"

def api(path, payload):
    req = urllib.request.Request(BASE + path, data=json.dumps(payload).encode(),
        headers={"Authorization": "Bearer " + TOK, "Content-Type": "application/json"})
    return json.load(urllib.request.urlopen(req, timeout=60))

def embed(texts, model="bge-m3"):
    """把一批文本编码成 (N, dim) 的向量矩阵；注意【入库与查询必须同一个 model】"""
    r = api("/embeddings", {"model": model, "input": texts})
    return np.array([x["embedding"] for x in r["data"]], dtype=np.float32), r["usage"]

def cosine(q, M):
    """查询向量 q 与矩阵 M 每一行的余弦相似度。先各自归一化再点积 = 余弦。"""
    qn = q / (np.linalg.norm(q) + 1e-9)                       # ★ 1e-9 防除零
    Mn = M / (np.linalg.norm(M, axis=1, keepdims=True) + 1e-9)
    return Mn @ qn

if __name__ == "__main__":
    DOCS = [
        "切片决定了 RAG 检索的最小单位，切得太碎会丢失语义。",
        "向量检索通过计算查询向量与文档向量的余弦相似度，召回最相关的片段。",
        "重排（Rerank）用交叉编码器对候选片段重新打分，通常能显著提升检索精度。",
        "温度参数控制生成文本的随机性，温度越高输出越随机。",
        "Function Calling 让模型输出结构化的工具调用请求。",
    ]
    QUERY = "怎么让检索结果更准？"

    D, u = embed(DOCS)
    print(f"向量维度 = {D.shape[1]}，usage = {u}")
    qv, _ = embed([QUERY])
    sims = cosine(qv[0], D)
    for r, i in enumerate(np.argsort(-sims), 1):
        print(f"#{r}  cos={sims[i]:.4f}  {DOCS[i]}")
```

**本机实测输出（2026-11-09 实跑，非杜撰）**

```
① 对 5 条文档做 embedding：
   bge-m3 向量维度 = 1024，usage = {'prompt_tokens': 122, 'total_tokens': 122}
   向量前 5 维（doc0）= [-0.0232, -0.0033, -0.0373, -0.0034, -0.0107]

② 查询「怎么让检索结果更准？」+ 余弦相似度 TopK（纯向量检索）：
   #1  cos=0.6222  doc2: 重排（Rerank）用交叉编码器对候选片段重新打分，通常能显著提升检索精度。
   #2  cos=0.5997  doc1: 向量检索通过计算查询向量与文档向量的余弦相似度，召回最相关的片段。
   #3  cos=0.5839  doc0: 切片决定了 RAG 检索的最小单位，切得太碎会丢失语义。
   #4  cos=0.4743  doc4: Function Calling 让模型输出结构化的工具调用请求。
   #5  cos=0.4621  doc3: 温度参数控制生成文本的随机性，温度越高输出越随机。
```

**停下来想一秒的地方**：查询是"**怎么让检索结果更准？**"，**没有出现"重排"两个字**，但向量检索把"重排能提升检索精度"排到了 **#1**（cos=0.6222），而完全跑题的"温度参数""Function Calling"被压到 #4/#5。**这就是"语义"而不是"字面"在起作用。**

- **逐行要点**
  - `d["desktop"]["bootstrapAuth"]` ❌ → `d["desktop.bootstrapAuth"]` ✅：配置解码后是**扁平点号键**，`desktop.bootstrapAuth` 本身就是顶层键名。写错会直接 `KeyError`。
  - `embed()` 强制"入库与查询走同一个 model"：把模型名做成参数，但**调用方必须传一致的值**——这是 RAG 最常见的低级事故。
  - `cosine()` 里 `+1e-9`：零向量或极短文本的模接近 0，不加会给 `nan`。
  - `np.argsort(-sims)`：**负号 = 从大到小**。`argsort` 默认升序，忘了负号会把最不相关的排第一。
  - 归一化后点积：因为余弦只看夹角，先归一化再内积是标准写法，比逐个算 arccos 快且稳。
- **踩坑提示**
  1. **入库/查询模型必须一致**：今天 `bge-m3`（1024 维）与 `text-embedding-3-small`（1536 维）**维度都不同**，混用会直接报错或算出垃圾。**换模型 = 全量重算 + 重建索引。**
  2. **相似度分数别当绝对阈值**：实测 0.6222 与 0.4743 有区分度，但这是**同一批候选内相对排序**；跨查询/跨模型不可比。要设阈值，得在**你自己的数据分布上标定**。
  3. **中文注意 `usage`**：本例 5 条文档 122 token。**向量化是入库成本**（一次性）× **查询向量化是每次提问成本**（高频）——小文档便宜，但海量文档 + 高频查询要算进预算。
  4. **`bge-m3` 支持多语言/长文本**，但**别指望它替代关键词**：型号、编号这类精确串它反而不如 BM25。见动手任务。
  5. **端点用量计费**：这些调用消耗的是你自己账号额度，只适合本地联调，不要写进对外产品。

- **动手任务（20 分钟）**：把上面代码里的 `DOCS` 换成一组**含"精确串"的文档**（例如混入"订单号 A12345 状态：已发货""iPhone 17 Pro 保修期 12 个月"），再用两个查询各跑一次：① 语义型"我的手机保修多久" ② 精确型"订单号 A12345 的状态"。**观察向量检索对哪个更靠谱**：语义型它通常能命中，精确型它可能把"订单号 A67890"也召回来。结论：**该上混合检索**（关键词保精确 + 向量保语义）。
- **与我的工作结合**
  - **Android（端侧/离线知识问答）**：把 `assets/` 里的知识文档在**构建期**算好向量并打包进 `assets`（见 11-06 切片那讲），运行时只做"查询向量 → 本地暴力/小型 ANN 检索 → 喂端侧 LLM"。**约束**：端侧要离线，就得把 embedding 也搬到端上（`MediaPipe` 有端侧 embedder）或**在构建期预计算文档向量、只把查询向量交给一个轻量端侧模型**。内存与包体积是硬约束，维度别开太大。
  - **前端 / 小程序**：做"帮助中心智能问答"时，**向量索引放服务端**（小程序包体积有硬限制），客户端只发查询、拿回命中的 chunk。要支持"检索不到时关键词兜底"，因为向量对**精确串**就是弱项。
  - **一句话迁移**：你熟 `HashMap` 按 key 精确查，向量检索是**按"意思"近似查**——从"相等匹配"升级到了"最近邻匹配"。这跟你在 Android 里用 `RecyclerView` 找"相似的 item 做缓存复用"是同一种"找最近"的直觉。

## 5 明日预告与待复习（8 min）

- **明日主题**：W3 · 第 3 讲 —— **重排（Rerank）**。今天向量检索给出了 TopK，但 TopK 里**顺序未必对**；明天讲：为什么"粗召回 + 精排"要分两段、交叉编码器（cross-encoder）和双塔（bi-encoder）差在哪、重排能救什么、救不了什么。
- **待复习（3 条，今天必须记住）**
  1. **向量检索 = 把"意思像不像"变成"夹角小不小"**；余弦相似度只看向量方向，不看长度。
  2. **入库与查询必须用同一个 embedding 模型**；换模型 = 全量重算 + 重建索引。
  3. **向量不是万能的**：精确串（型号/编号）关键词更强，生产上多是**混合检索**；相似度**分数不能当绝对阈值**，只能在同批候选内相对比较。
- **一句话复盘**：最容易忘的是——**今天这个"TopK"就是明天重排的输入**。向量检索的定位是"**快速粗筛，宁滥勿缺（recall 优先）**"，而不是"一步到位排准"。明天你会亲眼看到：粗筛把对的排到了第二，是重排把它拎回第一。
