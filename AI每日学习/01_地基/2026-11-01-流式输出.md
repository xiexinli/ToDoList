## 1 概念精讲（30 min）

**一句话定义**
流式输出 = 服务端把一次生成拆成很多个"增量块（delta）"，用 `text/event-stream`（SSE）协议**每生成一小段就推一次**，客户端边收边渲染；而不是等内容全部生成完再一次性返回一个 JSON。

**它解决什么问题 / 为什么现在必须懂**
1. **感知延迟**。一句话答案 3 秒出完 vs 一段 800 字回答 25 秒出完——后者如果整段返回，用户面对的是 25 秒白屏。流式把"25 秒白屏"变成"0.6 秒出第一个字，然后持续在动"。
2. **可中断**。长回答里用户看到前两句就知道跑偏了，能立刻取消，省掉后面所有 token 的钱。非流式做不到。
3. 这是后面 Agent、工具调用回放、思考过程展示的**共同底座**——没有流式，做不出"边想边做"的交互。

**关键机制**

```
非流式：
  客户端 ──POST──► 服务端 ──[生成完整答案: 25s]──► 一次性返回 {...whole answer...}
  用户看到的：25 秒白屏 → 突然出现全文

流式：
  客户端 ──POST──► 服务端
           ◄── data: {"delta":{"content":"你"}}          t=0.6s  ← TTFT，用户看到第一个字
           ◄── data: {"delta":{"content":"好"}}          t=0.9s
           ◄── data: {"delta":{"content":"，"}}          t=1.2s
           ...   (每个 chunk 都是"新增的那一点"，不是全量)
           ◄── data: {"delta":{},"finish_reason":"stop"} t=25s
           ◄──  连接关闭
  用户看到的：马上开始出字，一直在动
```

**SSE 协议要点（`text/event-stream`）**
- 每条消息形如 `data: <payload>\n\n`（**两个换行**才是消息结束）；
- payload 是 JSON，长这样：`{"choices":[{"delta":{"content":"你"},"index":0}]}`；
- 关键区别：非流式里字段叫 `message.content`，流式里叫 **`delta.content`**，而且是**增量**，要自己字符串拼接；
- OpenAI 标准还会在最后发一行 `data: [DONE]` 表示正常结束。

**一个 chunk 里可能装的东西比你想的多**
| 位置 | 含义 |
|---|---|
| `delta.content` | 正文增量 |
| `delta.reasoning_content` | **思考过程**增量（推理模型会先推一大段这个） |
| `delta.tool_calls` | 工具调用的**分段**参数（要按 `index` 拼接，见 W2 第 4 讲） |
| `finish_reason` | 最后一个 chunk 才有，`stop` / `length` / `tool_calls` |
| `usage` | **只有显式开启 `stream_options.include_usage` 且服务端支持时才给** |

**常见误区**
1. **"流式让回答变快了。"** 不，总生成时间基本不变。它降低的是 **TTFT（Time To First Token）** 和"用户感觉等了多久"。真正让总时间变短的是投机解码、更快的模型这类手段。
2. **"流式也能拿到 usage。"** 本机实测：**整个流里没有任何 usage 块**。要统计 token，得另发一次非流式请求，或者本地估算。
3. **"流式断了能自动续上。"** 没有这种事。连接一断，已生成的部分在你的缓冲区里、模型侧的状态已经丢了，只能重发。生产代码必须自己处理重试。

**① 手写版 `stream_raw.py`（零依赖，直击协议）**

```python
# stream_raw.py —— 不借助任何 SDK，手写 SSE 流式解析
# 目的：看清"流式"到底在网络上长什么样。Python 3.9+，零第三方依赖。
import json
import os
import time
import urllib.request

URL = "https://www.dhcoder.net/llm-api/v1/chat/completions"
TOKEN = os.environ["DHWORK_TOKEN"]

body = {
    "model": "deepseek-v4-flash-dhwork",
    "messages": [{"role": "user", "content": "用三句话解释什么是大模型的流式输出。"}],
    "stream": True,          # ← 唯一的开关
    "max_tokens": 600,       # 推理模型要给足预算，否则正文为空
}

req = urllib.request.Request(
    URL,
    data=json.dumps(body).encode("utf-8"),
    headers={
        "Content-Type": "application/json",
        "Authorization": "Bearer " + TOKEN,
    },
)

t0 = time.time()
first_token_at = None
answer_parts = []

# urlopen 返回的对象支持"逐行迭代"——这是流式的关键：
# 它不会等整个响应体到齐，而是每收到一行就 yield 一行
with urllib.request.urlopen(req, timeout=120) as resp:
    print("Content-Type:", resp.headers.get("Content-Type"))
    for raw_line in resp:
        line = raw_line.decode("utf-8", "ignore").strip()

        if not line:                      # SSE 用空行分隔消息，跳过
            continue
        if not line.startswith("data:"):  # 忽略注释行 / 心跳行（有些网关会插 ': ping'）
            continue

        payload = line[len("data:"):].strip()
        if payload == "[DONE]":           # OpenAI 标准的结束标记
            break

        chunk = json.loads(payload)
        delta = chunk["choices"][0]["delta"]

        # 推理模型会先推一段 reasoning_content（思考过程），再推 content（正文）
        if delta.get("reasoning_content"):
            continue                      # 本示例丢弃思考过程，只看正文
        piece = delta.get("content")
        if piece:
            if first_token_at is None:
                first_token_at = time.time() - t0
            answer_parts.append(piece)
            print(piece, end="", flush=True)   # flush：不加它你会"攒着一次打出来"

print()
print(f"\n--- TTFT（首字延迟）= {first_token_at:.2f}s  总耗时 = {time.time() - t0:.2f}s")
print("--- 拼接结果:", "".join(answer_parts)[:60], "...")
```

**本机实测输出（2026-11-05 补写时实跑，非杜撰）**

```
Content-Type: text/event-stream; charset=utf-8
大模型的流式输出是指模型在生成文本时，不是等全部内容生成完毕后再一次性返回，而是按顺序逐步生成并即时发送每个词或片段……
--- TTFT（首字延迟）= 2.04s  总耗时 = 3.06s   本次共 307 行 chunk，正文 127 字

对照 —— 同一个问题改走【非流式】：
--- 首字节到达 = 3.56s（= 总耗时，因为它是"全部到齐"才算到达）  正文 113 字
```

**本机端点的两个非标准行为（实跑确认）**
1. **不发 `data: [DONE]`**。实测采集 41 行 chunk，**没有任何一行包含 `[DONE]`**。所以循环不能只靠 `[DONE]` 退出，必须同时把"连接关闭"当成正常结束。
2. **不开 `stream_options.include_usage` 就没有 usage**；实测即使传了该参数，本机端点也**没返回 usage 块**。

**② SDK 版 `stream_sdk.py`（生产写法）**

```python
# stream_sdk.py —— openai>=1.40.0 的流式写法，含取消与异常处理
import os
from openai import OpenAI, APIError, APIConnectionError

client = OpenAI(api_key=os.environ["DHWORK_TOKEN"],
                base_url="https://www.dhcoder.net/llm-api/v1")

def stream_chat(prompt: str, model: str = "deepseek-v4-flash-dhwork"):
    """生成器：逐段 yield 正文文本。调用方决定怎么渲染、什么时候 break。"""
    stream = client.chat.completions.create(
        model=model,
        messages=[{"role": "user", "content": prompt}],
        stream=True,
        max_tokens=600,
    )
    try:
        for chunk in stream:
            if not chunk.choices:        # 有些服务端会发只带 usage 的空 choices 块
                continue
            delta = chunk.choices[0].delta
            if delta.content:            # 只取正文，忽略 reasoning_content
                yield delta.content
    except (APIConnectionError, APIError) as e:
        yield f"\n[流中断: {e}]"          # 流式必须自己兜异常，否则会静默截断
    finally:
        stream.close()                   # ★ 主动关闭，防止连接泄漏


if __name__ == "__main__":
    for piece in stream_chat("用三句话解释什么是大模型的流式输出。"):
        print(piece, end="", flush=True)
    print()
```

- **逐行要点**
  - `for raw_line in resp`：**不要**用 `resp.read()`——那是"等全部到齐"，流式就白搭了。
  - `flush=True`：终端默认行缓冲，不加它你会以为流式没生效。
  - `chunk.choices` 可能是**空列表**，直接取 `[0]` 会 IndexError。
  - `stream.close()`：放在 `finally` 里。用户点"停止生成"时，你 `break` 出循环就够了吗？不够——**底层 HTTP 连接仍然开着**，长会话下会耗尽连接池。
- **踩坑提示**
  1. **反向代理会吃掉流式**。Nginx 默认 `proxy_buffering on` 会把 chunk 攒起来再下发，你的"流式"变成"最后一次性到达"。修法：`proxy_buffering off;` + 响应头 `X-Accel-Buffering: no`。
  2. **Android（OkHttp）不能 `response.body!.string()`**。它会把整个响应体读进内存，等于非流式。要 `response.body!!.source()` 配 `BufferedSource.readUtf8Line()` 逐行读。
  3. **不要对报错文案做字符串匹配**。本机端点的 400 文案是 Anthropic 口径（如 `Invalid type for 'input'`），跨服务商完全不稳定——**只判断 HTTP 状态码**。
  4. **`delta.tool_calls` 是分片到达的**。工具名可能在第一个 chunk，参数字符串会被切成好几段，必须按 `index` 拼起来再 `json.loads`（W2 会专门讲）。

- **明日主题**：少样本提示（Few-shot / In-Context Learning）——进入 W2「Prompt 工程与工具调用」。
- **待复习（3 条，今天必须记住）**
  1. 流式优化的是 **TTFT / 感知延迟**，不是总耗时；字段从 `message.content` 变成 **`delta.content`** 且是增量。
  2. 结束判断不能只靠 `[DONE]`——**本机端点根本不发它**，必须把"连接关闭"也当正常结束。
  3. 流式的**取消**要显式 `close()` / `cancel()`，`break` 出循环不等于断开连接。
- **一句话复盘**：最容易忘的是——**流式是端到端的**：模型端开了、Nginx 缓冲开着、OkHttp 用了 `.string()`，任何一环掉链子，"流式"就退化成"最后一次性出现"。
