## 1 概念精讲（30 min）

**一句话定义**
文本切片（Chunking）= 在**入库之前**，把一篇长文档切成若干个较短的、语义尽量完整的片段（chunk）；每个 chunk 是 RAG 里**被向量化、被存储、被检索的最小单位**。

> 一句话记住本质：**切片决定了"什么算一个可以被检索的意思单元"。** 你问一句话，系统不会去找"整篇文档"，只会去找"和这句话最像的几块"——那几块就是你切出来的。

**它解决什么问题 / 为什么现在必须懂**
1. **物理约束**：embedding 模型和 LLM 都有输入长度上限。一篇 5 万字的制度文档没法整篇塞进去。
2. **精度约束**：就算塞得下，"整篇文档"的向量是**所有主题的平均**，跟任何具体问题都不够像。切小，才能让向量聚焦。
3. **成本约束**：向量库存的是 chunk 的向量。chunk 越碎越多，检索越"轻"但越容易断章；越大越少，越省但越糊。
4. **这是 RAG 里 ROI 最高的环节之一**：后面的 embedding 模型、向量库、重排都可以换，但**切片切错了，换什么都不救**。

**关键机制：切片在整条链路里的位置**

```
                    ┌─────────── 离线（入库）───────────┐
  长文档 ──► 【切片 Chunking】──► chunk₁ chunk₂ chunk₃ … ──► 各自 Embedding ──► 向量库
                     ↑ 今天讲这里                                  (W3 第 2 讲)
                    └─────────── 在线（提问）───────────┐
  用户问题 ──► Embedding ──► 相似度检索 TopK ──► 命中的 chunk ──► 拼进 Prompt ──► LLM 生成答案
                (W3 第 2 讲)                                      (W3 第 3 讲：引用与防幻觉)
```

**检索的最小单位 = 切片的最小单位。** 这个等式是今天唯一必须刻进脑子里的东西。

**三条主流切法**

| 切法 | 怎么切 | 优点 | 代价 |
|---|---|---|---|
| **定长**（fixed-size） | 每 N 个字符/ token 一刀 | 最简单、大小可控 | 会**切断句子、词语、代码** |
| **递归字符**（recursive） | 按分隔符优先级：段落 → 换行 → 句号 → 空格 → 硬切 | 尽量在语义边界断开，工程上最常用 | 块大小不完全均匀 |
| **结构/语义切分** | 按 Markdown 标题、代码块、或语义相似度断点 | 语义最完整 | 实现复杂、慢；要针对文档类型定制 |

**两个绕不开的参数**
- `chunk_size`：块的大小。**注意它到底按"字符"还是按"token"**——这是新手最容易踩的坑（见下）。
- `chunk_overlap`：相邻块之间**重叠**的字符数。它是给"正好被切断的答案"留的一根救命绳：一个完整答案被切成两半，只要它同时出现在两块里，检索时至少命中一块。

**四种常见切法对照（同一段话，size≈60）——今天代码里会实跑出来**
- 定长会把"切片。切得太碎…"从**句子中间**切断；
- 递归会尽量停在**句号处**（"……取决于切片。"）；
- 这就是"为什么不能只按字数切"的最直观证据。

**常见误区**
1. **"chunk 越大信息越全，越大越好。"** 错。**chunk 太大 → 向量被平均成"四不像" → 检索精度断崖式下降**（这也是为什么"把整篇文档当一个 chunk"是最差的做法之一）。反过来切太碎，一个完整答案被拆到三块里，谁都不够像。**切片的核心就是在"语义完整"和"检索精度"之间找平衡点。**
2. **"按固定字数切就够了，简单。"** 固定字数会**在句中/词中/代码块中间切断**（`...co`｜`nst x =`），中文还涉及全角标点。真实文档类型多样，纯定长几乎总是次优解。
3. **"overlap 可有可无，省点空间。"** overlap=0 时，**答案正好落在两块边界上就彻底丢失**。但 overlap 也别贪大，它是**冗余**：越大，向量库越膨胀、检索越容易返回重复内容。经验值约 **size 的 10%~20%**。
4. **"切片是一次性的、写完就不管了。"** 切片策略必须和**问题类型**匹配（FAQ 短问短答 vs 长文档问答 vs 代码检索，最优参数完全不同），并且**一旦入库，改切片 = 全量重算 embedding = 真金白银**——所以切片参数要尽早定稿并**版本化**。

> 补充（不展开，W3 第 3 讲会用）：切片时**顺手把元数据一起存**——`source`（哪篇文档）、`标题路径`、`页码`、`chunk_index`。没有它们，后面做"引用来源"和"排查为什么检索错了"都无从下手。

## 2 代码片段（40 min）

- **场景**：一个**零依赖、可直接运行**的切片器 + **质量体检器**。它实现"定长"和"递归字符"两种切法（含重叠），并提供 `audit()` 用**指标**给切片打分；最后拿本机真实文件（2026-11-05 的学习材料）跑对照实验。用途很实在：**在项目里决定 chunk_size / overlap 之前，先用它量一量，而不是拍脑袋。**
- **依赖与版本**：**零第三方依赖**（仅标准库 `re` / `typing`），Python 3.9+ 直接可跑（本机实测环境 Python 3.9.6）。token 估算用**手写启发式**，真实项目请替换成 `tiktoken`（OpenAI）或目标模型自带 tokenizer。

**完整代码 `chunker.py`**

```python
# chunker.py —— 零依赖（仅标准库）文本切片：定长 / 递归字符 + 质量体检
# Python 3.9+ 直接可跑，不依赖 langchain / tiktoken
import re
from typing import Dict, List

# ── 0. 粗略 token 估算（中文与英文用不同系数；真实项目请换 tiktoken / 模型自带 tokenizer）
def est_tokens(s: str) -> int:
    cjk = len(re.findall(r"[一-鿿]", s))     # 统计中文字符
    other = len(s) - cjk
    return int(cjk * 0.7 + other / 4) + 1            # 中文约 0.7 token/字，英文约 1 token/4 字符


# ── 1. 定长切片：最省事，也最容易在句子/词语中间切断
def fixed_chunks(text: str, size: int = 300, overlap: int = 60) -> List[str]:
    step = max(1, size - overlap)           # ★ overlap 必须 < size，否则 step<=0 会死循环
    return [text[i:i + size] for i in range(0, len(text), step) if text[i:i + size].strip()]


# ── 2. 递归字符切片：按「分隔符优先级」逐层下降，是 langchain 的经典做法
DEFAULT_SEPARATORS = ["\n\n", "\n", "。", "！", "？", "；", ".", " ", ""]

def recursive_chunks(text: str, size: int = 300, overlap: int = 60,
                     separators: List[str] = None) -> List[str]:
    seps = separators if separators is not None else DEFAULT_SEPARATORS

    def split(t: str, seps: List[str]) -> List[str]:
        if len(t) <= size:
            return [t]
        if not seps:                        # 分隔符用尽 → 只能硬切
            return [t[i:i + size] for i in range(0, len(t), size)]
        sep, rest = seps[0], seps[1:]
        parts = t.split(sep)
        pieces: List[str] = []
        for p in parts:
            piece = p + sep if p is not parts[-1] else p   # ★ 把分隔符归回前一段，别丢标点
            if len(piece) <= size:
                pieces.append(piece)
            else:
                pieces.extend(split(piece, rest))          # ★ 还太大 → 用下一级分隔符再切
        # 贪心合并小碎片，避免产生大量「孤儿块」（只有一句话的块）
        merged, buf = [], ""
        for p in pieces:
            if len(buf) + len(p) <= size:
                buf += p
            else:
                merged.append(buf)
                buf = p
        if buf:
            merged.append(buf)
        return merged

    chunks = [c for c in split(text, seps) if c.strip()]
    if overlap <= 0:
        return chunks
    out: List[str] = []
    for i, c in enumerate(chunks):
        if i == 0:
            out.append(c)
        else:
            out.append(chunks[i - 1][-overlap:] + c)       # ★ 拼上一块尾部，缓解「答案被切断」
    return out


# ── 3. 质量体检：切片好不好，不靠眼睛看，靠指标
def audit(chunks: List[str]) -> Dict[str, float]:
    lens = [len(c) for c in chunks]
    avg = sum(lens) / len(lens)
    too_short = sum(1 for L in lens if L < avg * 0.4)      # 孤儿块：远短于平均，语义多半不完整
    return {
        "块数": len(chunks),
        "平均字数": round(avg, 1),
        "最短": min(lens),
        "最长": max(lens),
        "孤儿块数": too_short,
        "估算总token": sum(est_tokens(c) for c in chunks),
    }


if __name__ == "__main__":
    SENTENCE = ("RAG 的检索质量，八成取决于切片。切得太碎，一个完整答案被拆到三个块里，"
                "检索时谁都不够像；切得太大，一个块里塞了三个主题，向量被平均成四不像。"
                "所以切片的本质，是在「语义完整」和「检索精度」之间找平衡点。")
    print("【A】同一段文字，两种切法的对比（size=60）")
    print("定长（fixed）  :", fixed_chunks(SENTENCE, 60, 12)[0])
    print("递归（recursive）:", recursive_chunks(SENTENCE, 60, 12)[0])

    print("\n【B】真实文件切片体检：2026-11-05-FunctionCalling与工具调用.md")
    path = "/Users/alion/DemoProjects/ToDoList/AI每日学习/01_地基/2026-11-05-FunctionCalling与工具调用.md"
    with open(path, encoding="utf-8") as f:
        doc = f.read()
    print("原文长度：", len(doc), "字，估算", est_tokens(doc), "token")
    for name, fn in [("fixed", lambda t: fixed_chunks(t, 600, 120)),
                     ("recursive", lambda t: recursive_chunks(t, 600, 120))]:
        print(f"  {name:10s} -> {audit(fn(doc))}")
```

三处值得你停下来想一秒的地方：

1. **【A】是今天的核心证据**：同一段话，定长切出来**停在"三个主"这种词中间**，递归切出来**停在句号处**。这就是"语义边界"的直观差别。
2. **【B】的两行对比**：`recursive` 的**孤儿块数 = 0**，而 `fixed` = 1——递归切分把"只有一句话的小碎片"合并掉了，块大小更均匀。
3. **`recursive` 的最长 = 717 > size 600**：不是 bug，是 **overlap 拼上了上一块的尾部（600 + 120 ≈ 720）**。记住：**开启 overlap 后，实际块长 ≈ size + overlap**，算"会不会超模型上限"时要把 overlap 算进去。

- **逐行要点**
  - `est_tokens` 用中文/英文**不同系数**的启发式。要刻进脑子里的一条：**"字符数"不等于"token 数"**——中文 1 字 ≈ 0.7 token，英文约 4 字符 ≈ 1 token。判断"块会不会超模型上限"时，**必须先换算成 token**。
  - `step = max(1, size - overlap)`：`overlap ≥ size` 会让 `step ≤ 0`，`range(..., 0)` 直接报错（或死循环）。**overlap 一定小于 size。**
  - 递归切分的灵魂是**分隔符优先级**列表 `["\n\n", "\n", "。", "！", "？", "；", ".", " ", ""]`：段落 → 换行 → 中文句号 → …… → 空格 → 空串（硬切）。**先按大的语义单位切，不满足再降级**——这就是"尽量在语义边界断开"的实现方式。
  - `piece = p + sep if p is not parts[-1] else p`：`str.split` 会**吃掉分隔符**，必须手动还回前一段，否则拼回的句子会丢标点、甚至丢换行。
  - 贪心合并（`merged / buf`）：这一步专门治**孤儿块**。没有它，递归切分会产出大量"一句话块"，`audit` 里的孤儿块数会飙高。
  - `audit` 里最有用的单一指标是 **孤儿块数**：它等于"远短于平均长度的块数"。**它高，就说明切太碎了**——比"块数"和"平均长度"更能一眼看出问题。
- **踩坑提示**
  1. **字符 ≠ token**：按"300 字"切，中文可能已 200+ token，代码/英文又不一样。真实项目**要么用 `tiktoken` 真数 token，要么给模型上限打足余量（如只用 60%）**。
  2. **`overlap ≥ size` 会炸**：`step ≤ 0`。经验值 overlap = size 的 10%~20%；且**算上限时用 `size + overlap`**，别只看 size。
  3. **别在结构中间断开**：代码块（三反引号）、表格、Markdown 标题——切断了，检索到半截代码/表格模型也读不懂。做法：**先按结构（标题层级 / 代码块）切，再对"超长的单个结构块"做递归切**（结构切 + 递归切的组合）。
  4. **中文分隔符必须用全角**：`。！？；`，不是 `. ! ? ;`。**分隔符集写错，递归切分就悄悄退化成"按空格/硬切"**——代码跑得通，只是效果变差，不容易发现。
  5. **切片是"入库前"的事，改一次要全量重算**：一旦向量入库，改切片策略 = 所有 embedding 重算 = 花钱花时间。所以**切片参数要尽早定稿并版本化**（记录每个 chunk 用的是哪套策略）。
  6. **元数据要跟着 chunk 一起存**：`source / 标题路径 / 页码 / chunk_index`。**不存，后面做引用和排错就全靠猜**（W3 第 3 讲会用到）。

- **与我的工作结合**
  - **Android（端侧 RAG / 离线知识问答）**：把 `assets/` 里的知识文档在**构建期**切好片（写成 Gradle task），运行时只做"查询向量 → 本地向量库 TopK → 喂给端侧 LLM"。关键约束：**切片参数要在构建脚本里固定并版本化**（改一次要重新打包）；端侧内存与包体积有限，`chunk_size` 别开太大；还要支持"只更新单个文档"的增量重建，而不是整库重算。这条路径和 W4 的"端云协同"能直接接上。

- **待复习（3 条，今天必须记住）**
  1. **检索的最小单位 = 切片的最小单位**：切什么，检索就只能找到什么。
  2. **chunk 太大 → 向量被平均、检索变糊；太小 → 语义碎片化。** 加上 `overlap` 这根"救命绳"，**且 overlap 一定小于 size**。
