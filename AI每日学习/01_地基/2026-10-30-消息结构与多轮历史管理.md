## 1 概念精讲（30 min）

**一句话定义**
消息（message）是带 `role` 标签的一条记录；`messages` 是这些记录按时间顺序排成的数组。**你真正发给模型的，是这个数组，不是一段文字。**

**它解决什么问题 / 为什么现在必须懂**
1. 昨天搞清了"发多少 token"，今天要搞清"发的是什么结构"。聊天、RAG、Agent——所有 LLM 应用最终都落成这个数组。
2. **角色 = 权限层级**：system 的话模型最听，user 次之。规则写错位置，它就不生效——而且往往**不报错**（今天实测踩到了，见下文）。
3. **角色 = 状态机**：assistant 消息是"我上一轮说过的话"的回放，tool 消息是"工具跑完的结果"。不会维护这个数组，就做不出多轮对话，也做不出 Agent。

**关键机制**

① 四种角色，各自的岗位职责

| role | 谁写的 | 作用 | 能否省略 |
|---|---|---|---|
| `system` | **开发者** | 定人设、定规则、定输出格式与边界 | 可省，但省了就没人"钉"行为 |
| `user` | 用户 | 本轮诉求 | 必须有 |
| `assistant` | 模型（**由你的程序回填**） | 模型上一轮的回复，回放给它看 | 首轮没有 |
| `tool` | 你的程序 | 工具/函数执行结果，回填给模型 | 用到工具才需要（W2 讲） |

顺序不是随便排的，是一条严格时间线：

```
system ──→ user ──→ assistant ──→ user ──→ assistant ──→ user ──→（模型接着生成）
 规则      第1问    第1答(回填)    第2问    第2答(回填)    第3问
                     ↑ 这两条不是模型"记得"，是你的程序手动塞回去的
```

② **无状态 → 数组就是记忆**（昨天的结论在这里兑现）
服务端每轮都从零开始读你发过去的整个数组。第三轮还记得"我叫阿良"，纯粹是因为程序把 assistant 的回复 push 回了 history。**"记忆"是一个数据结构，不是一个模型能力。**

③ **角色是"权限"，不是"格式"**
模型被训练成：越靠上的角色，指令优先级越高 → `system > user`。所以"只准输出 JSON"这类硬约束必须写进 system；写在 user 里，随时可能被后续用户内容顶掉。

**常见误区**
1. 很多人以为"system 就是个可有可无的开场白"。其实它是**唯一能稳定压制用户输入的位置**——做结构化输出、做安全边界，system 是主战场。今天代码 ①/② 的对比就是现场证据：同一句话，没有 system 时模型自己发挥成一段散文，有 system 时被直接压成一行 JSON。
2. 很多人以为"把历史全塞进去 = 记忆好"。其实每多一轮，`prompt_tokens` 就稳定多一段（今天实测 37 → 62 → 86，**每轮 +24~25**），而长历史的中间部分还容易被忽略。**记忆是要设计的，不是攒的。**
3. 很多人以为"assistant 消息是模型自己存的"。其实那是**你的程序**把回复写回数组的；忘了回填，就会得到"模型失忆"的假象（代码 ④ 实测）。

## 2 代码片段（40 min）

**场景**
用一个脚本同时验证四件事：① system 到底管不管用；② 多轮对话的历史是怎么一步步长出来的（顺带看 `prompt_tokens` 怎么涨）；③ 为什么"关掉重开就失忆"；④ 历史裁剪的必要性从哪来。

**依赖与版本**
零依赖——只用 Node.js 内置 `fetch`（Node 18+ 即可）。本机实测 Node **v26.7.0**，无需 `npm install`。

**最小可运行代码**（保存为 `roles-history-demo.mjs`）

```javascript
// roles-history-demo.mjs —— 零依赖，Node 18+ 直接跑：node roles-history-demo.mjs
// 今日主题：消息结构（Roles）+ 无状态下如何亲手维护多轮历史
const BASE_URL = process.env.LLM_BASE_URL || 'https://api.openai.com/v1';
const API_KEY  = process.env.LLM_API_KEY;
const MODEL    = process.env.LLM_MODEL;
if (!API_KEY || !MODEL) { console.error('缺少 LLM_API_KEY / LLM_MODEL'); process.exit(1); }

// 统一的请求函数：OpenAI 兼容接口的四件套
async function chat(messages, opts = {}) {
  const res = await fetch(`${BASE_URL}/chat/completions`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${API_KEY}` },
    body: JSON.stringify({ model: MODEL, messages, ...opts }),
  });
  if (!res.ok) throw new Error(`HTTP ${res.status}: ${(await res.text()).slice(0, 300)}`);
  return res.json();
}
const say = (s) => s.choices[0].message.content.trim();
const line = (t) => console.log(`\n===== ${t} =====`);

const Q = '客户说：订单 20261030-AB9 少发了一件，我很生气。请判断这句话的情绪与意图。';

// ① system 角色：同一句话，带与不带系统提示
line('① 不带 system —— 模型自己决定怎么答');
console.log(say(await chat([{ role: 'user', content: Q }])).slice(0, 200));

line('② 带 system —— 把角色、格式、边界一次性钉死');
const SYSTEM = [
  '你是一个电商客服工单分类器。',
  '只输出一行 JSON，字段固定为 intent（退款/补发/咨询）、emotion（平静/不满/愤怒）、need_human（true/false）。',
  '不要输出任何解释、Markdown 代码块或多余文字。',
].join('\n');
console.log(say(await chat([{ role: 'system', content: SYSTEM }, { role: 'user', content: Q }])));

// ③ 无状态 → 亲手维护历史：三轮连续对话
line('③ 三轮对话，历史由客户端每轮重放');
const history = [
  { role: 'system', content: '你是订单助手，回答不超过 20 字。' },
];
async function turn(userText) {
  history.push({ role: 'user', content: userText });
  const r = await chat(history);
  const a = say(r);
  history.push({ role: 'assistant', content: a });   // ★ 关键：把模型的回复追加回历史
  console.log(`👤 ${userText}\n🤖 ${a}\n   ↳ 本轮 messages 条数=${history.length}  prompt_tokens=${r.usage.prompt_tokens}  total=${r.usage.total_tokens}`);
  return r;
}
await turn('我叫阿良，订单号 20261030-AB9。');
await turn('我的订单号是多少？');
await turn('我叫什么？');

// ④ 把历史清空再问同一句 —— 证明"记忆"其实躺在你的数组里
line('④ 清空 history 后再问同一个问题');
console.log(say(await chat([{ role: 'system', content: '你是订单助手，回答不超过 20 字。' },
                            { role: 'user', content: '我叫什么？' }])));
console.log('→ 模型没有失忆，是你的数组里没有它。');
```

**逐行要点**（只讲关键行）
- `history.push({ role: 'assistant', content: a })` —— 全脚本最关键的一行。把模型的回复写回数组，下一轮它才有"记忆"。**对"模型失忆"的所有抱怨，八成都源于漏了这一句。**
- `chat(history)` 传的是同一个数组的引用，push 之后自动变长。开发时最省事；生产里建议传副本（`chat([...history], ...)`）避免异步并发改到同一个数组。
- system 那三条是**一条一句**的写法：角色 / 格式 / 禁止项。第二条用"只输出一行 JSON"钉死格式，第三条专门堵住最常见的跑偏——**模型很爱给 JSON 套一个 ```json 代码块**。
- 每轮打印 `r.usage.prompt_tokens`：把"历史越长越贵"从概念变成肉眼可见的数字（37 → 62 → 86）。
- ④ 清空 history 再问：答案变成"我还不知道您的名字"。这不是模型故障，是数组空了。

**踩坑提示**（下面每一条都在 2026-10-30 本机实测过，含一条静默失败）

| 探针 | 现象 | 结论 |
|---|---|---|
| `system` 放最前 | ✅ 通过，约束生效 | 标准写法 |
| `system` 放中间 | ✅ 通过，约束**仍然生效** | 本机端点容忍；但**不要依赖**，统一放最前 |
| 角色名写成 `System`（大写） | ✅ **HTTP 200，但约束静默失效** | ⚠️ 被当成普通 user 处理，不报错。**最危险的一类坑** |
| 角色名写成 `human`（未知角色） | ❌ HTTP 400 | 角色名是**枚举**，全小写英文 |
| 连续两条 `user` | ✅ 通过，能理解 | 合法，但语义会变模糊 |
| 连续两条 `assistant` | ✅ 通过 | 合法 |
| `content` 为空字符串 | ❌ HTTP 400 | 空消息会被拒，组装历史时记得过滤 |
| 缺 `role` 字段 | ❌ HTTP 400 | 结构必须完整 |
| 只有 `tool` 消息、没有配对的 tool_call | ❌ HTTP 400 `No tool call found for function call output with call_id ...` | tool 消息必须与一次真实的工具调用配对（W2 细讲） |
| 多条 `system` | ✅ 通过，合并生效 | 合法，但建议收敛成一条，好维护 |

另外两条：
- **报错文案会"跑到别的服务商口径"上**：上面几个 400 的原文是 `Invalid type for 'input': expected a string, but got an object instead.` —— 本机端点把请求转译到了 Anthropic 风格（呼应昨天发现的 `cache_read_input_tokens` 字段）。**写通用代码时不要对报错文案做字符串匹配**，只判断 HTTP 状态码。
- **历史增长是线性的、没有免费的午餐**：今天实测每轮 +24~25 prompt_tokens（两条消息的模板开销约 14 + 内容本身）。真实 App 里一轮内容几百 token，20 轮就是几千——**裁剪策略是必需品，不是优化项**。

## 3 动手 / 联想（20 min）

**动手任务**（10~20 分钟，加一个函数就够）

给 ③ 那段加一个**滑动窗口裁剪**：system 永远保留，历史只留最近 N 轮，超了就丢最老的。然后跑第 4 轮问"我叫什么"，观察它是否"失忆"——你就亲手复现了所有聊天 App 的记忆策略取舍。

```javascript
// 插在 ③ 之前：裁剪函数 —— system 必留，历史只保留最近 maxTurns 轮
function trimHistory(msgs, maxTurns = 2) {
  const sys = msgs.filter(m => m.role === 'system');          // 规则永不丢
  const rest = msgs.filter(m => m.role !== 'system');
  // 每轮对话 = 1 条 user + 1 条 assistant，所以按消息条数截断
  return [...sys, ...rest.slice(-(maxTurns * 2))];
}
// 把 turn() 里改成：const r = await chat(trimHistory(history, 2));
```

进阶版（有余力再做）：不用丢弃，改用**摘要**——把最老的一轮让模型压成一句话，作为一条 `assistant` 或补充 `system` 消息放回数组头部。这就是 W4「上下文工程」的最小雏形。

**与我的工作结合**
- **Android（聊天类 App）**：`messages` 数组就是你的**会话状态**。做 AI 聊天功能时，把它序列化存进 Room / SQLite，App 重启后读出来即可续聊——这样你就理解了"云端会话列表"到底是什么。同时**别把全量历史每轮重放**，用滑动窗口 + 老历史摘要控制 prompt 体积，这是移动端 AI 功能成本失控的第一大来源。
- **Android（表单/结构化场景）**：今天 ①/② 的对比直接可用——把"只输出 JSON、不要代码块、不要解释"写进 system，再配合 `JSON.parse`，比在业务代码里写一堆正则去剥 ```json 包裹靠谱得多。
- **前端 / 小程序**：会话状态放 Pinia/Redux 时，注意"持久化到 localStorage"与"发给模型的数组"是两份数据，别混用。用户清空聊天记录时，要**同时**清这两份，否则会出现"界面上没了但模型还记得"的诡异体验。
- **衔接明天**：今天讲"发什么结构"，明天讲"这次生成该有多随机"——同一个请求体的另一半。
