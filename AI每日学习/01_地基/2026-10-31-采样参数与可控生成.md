## 1 概念精讲（30 min）

**一句话定义**
采样参数（sampling parameters）是决定"模型如何从下一个 token 的概率分布里挑出实际那一个"的旋钮。它们**不改变模型权重，只改变采样策略**。

**它解决什么问题 / 为什么现在必须懂**
1. 同一个 prompt，`temperature=0` 和 `temperature=1.5` 出来的东西可能完全是两个产品：一个是稳定的字段抽取，一个是发散的文案。
2. 上一讲我们解决了"发什么结构"，这一讲解决"**同样的输入怎样稳定地复现同样的输出**"——这是能不能上生产的分水岭。
3. 不做参数分档，你的 AI 功能就会"今天对明天错"，测试同学第一条 bug 就是"结果不稳定"。

**关键机制**

一次生成的完整流水线（从左到右）：

```
输入 token
   │
   ▼
Transformer 前向 ──► logits（词表大小的原始分数，比如 15 万个浮点数）
   │
   ▼
① 温度缩放     logits / temperature      ← temperature
   │
   ▼
② softmax ──► 概率分布 p（所有词加起来 = 1）
   │
   ▼
③ 截断/重归一化                            ← top_k / top_p / min_p
   │   只留下"候选池"，池外的 token 概率清零再归一化
   ▼
④ 惩罚调整                                 ← presence_penalty / frequency_penalty
   │
   ▼
⑤ 按概率掷骰子（或用 seed 固定随机源）      ← seed
   │
   ▼
    选出 1 个 token ──► 拼回输入，循环下一步
```

**① temperature（温度）**：最直观的一个。`logits / T` 之后再 softmax。
- `T → 0`：分布被"拉尖"，最高分那个 token 概率趋近 1 → 退化成**贪心解码**（每步都选最大），最稳定。
- `T = 1`：模型原始分布。
- `T > 1`：分布被"压平"，小概率词也有机会被选中 → 更发散、也更离谱。
- 直觉记法：**温度 = 胆量**。

**② top_k（截断到前 k 个）**：只保留概率最高的 k 个 token，其余丢弃。固定数量，不管分布形状。k=1 就等于贪心。

**③ top_p（核采样 / nucleus sampling）**：从高到低累加概率，**累积到 p 为止**的那一批 token 入选。
- 关键区别：top_k 是"**数量**固定、**质量**浮动"；top_p 是"**质量**固定、**数量**浮动"。
- 分布很尖时，top_p=0.9 可能只留下 1～2 个 token；分布很平时，可能留下几百个。

**④ 惩罚项**：`presence_penalty` 惩罚"已经出现过"的 token（鼓励谈新话题），`frequency_penalty` 按出现次数累计惩罚（抑制复读）。两者取值一般 -2.0 ~ 2.0。

**⑤ seed**：固定随机源。**只对支持它的服务有效**，且不保证跨版本、跨批次的绝对一致（见误区）。

**常见误区**
1. **"temperature=0 就完全可复现。"** 很多人以为设 0 就能得到字节级一致的输出。其实：服务端可能同时批处理多个请求、MoE 模型的路由、浮点累加顺序、以及模型版本热更新，都会让结果漂移。工程做法是"**低温度 + 输出校验**"，而不是"指望它 100% 一样"。
2. **"temperature 和 top_p 要一起调。"** 官方文档的通用建议是**二选一**，只调一个。两个一起动，出问题时你根本分不清是哪个起作用。经验默认：`T=0`（确定性）或 `T=0.7 + top_p=1.0`（对话）。
3. **"top_p=0.9 是保留 90% 的 token。"** 不是按数量，是按**累积概率**到 0.9。词表 15 万，通常只有几十到几百个 token 入选。
4. **"参数在哪个模型上都一样。"** 本机实测就翻车了：`top_k` 直接 400，`gpt-5.6-terra-dhwork` 连 `temperature` 都不收（见第 2 段实测表）。

## 2 代码片段（40 min）

- **场景**：把"参数分档"固化成一个可复用的小模块——同一套代码，抽取类任务走确定档、对话走平衡档、创意走发散档。
- **依赖与版本**：`openai>=1.40.0`；Python 3.9+。
- ⚠️ **诚实声明**：本机（python3 3.9.6）**未安装 openai SDK**。本讲所有实测数据是用**等价的 `urllib` 请求**跑出来的（见文末"零依赖版"）；上面的 SDK 写法片段**未在本机执行过**，需先 `pip install "openai>=1.40.0"` 才能运行。
- **端点**：用你本机 DHwork 的 OpenAI 兼容端点（`https://www.dhcoder.net/llm-api/v1`），模型名如 `deepseek-v4-flash-dhwork` / `gpt-5.6-terra-dhwork`。

**① 参数分档模块 `sampling.py`**

```python
# sampling.py —— 采样参数分档：把"调参"变成"选档"
# 依赖：openai>=1.40.0
from dataclasses import dataclass, field, asdict
from typing import Optional, Dict, Any


@dataclass
class SamplingConfig:
    """一个档位 = 一组采样参数。字段名与 OpenAI API 对齐。"""
    name: str
    temperature: float = 1.0
    top_p: float = 1.0
    presence_penalty: float = 0.0
    frequency_penalty: float = 0.0
    seed: Optional[int] = None

    def to_kwargs(self) -> Dict[str, Any]:
        """转成可直接 ** 展开进 client.chat.completions.create() 的字典。"""
        d = asdict(self)
        d.pop("name")                                   # name 是我们的元数据，不能发给 API
        return {k: v for k, v in d.items() if v is not None}  # None 的参数不要发（有些端点拒收）


# 三个档位：几乎所有 LLM 应用都能归到这三类
DETERMINISTIC = SamplingConfig("deterministic", temperature=0.0, seed=42)          # 抽取/分类/路由
BALANCED      = SamplingConfig("balanced",      temperature=0.7, top_p=0.95)       # 对话/问答/总结
CREATIVE      = SamplingConfig("creative",      temperature=1.2, top_p=0.98,
                               presence_penalty=0.3, frequency_penalty=0.2)        # 文案/起名/头脑风暴

PRESETS = {"deterministic": DETERMINISTIC, "balanced": BALANCED, "creative": CREATIVE}
```

**② 跑一遍，观察"温度 = 胆量"**

```python
# demo.py —— 同一 prompt，三档各跑一次，对比输出与 token 消耗
# 运行：export DHWORK_TOKEN=$(...) 见下方"取令牌"一节
import os
from openai import OpenAI
from sampling import PRESETS

client = OpenAI(
    api_key=os.environ["DHWORK_TOKEN"],
    base_url="https://www.dhcoder.net/llm-api/v1",
)

PROMPT = "给一句 8 字以内的品牌口号，主题：咖啡"

for key in ("deterministic", "balanced", "creative"):
    cfg = PRESETS[key]
    resp = client.chat.completions.create(
        model="deepseek-v4-flash-dhwork",
        messages=[{"role": "user", "content": PROMPT}],
        max_tokens=600,          # ⚠️ 必须给足！这是推理模型，见"踩坑"第 1 条
        **cfg.to_kwargs(),
    )
    usage = resp.usage
    print(f"[{cfg.name:13}] {resp.choices[0].message.content!r}"
          f"  tokens={usage.total_tokens}")
```

**本机实测输出（2026-11-05 补写时实跑，非杜撰）**

```
[deterministic] '一杯唤醒世界'  tokens=266    # temperature=0
[creative     ] '咖啡唤醒灵感'  tokens=655    # temperature=2.0
```

> 注意 `tokens` 的差距：同一句 8 字口号，发散档的 **推理 token 数从 161 涨到 549**（见下方 usage 实测表）。**温度越高，模型"想"得越多，钱也花得越多**——这是很多人完全没意识到的一条成本线。

**③ 本机端点参数兼容性实测表（2026-11-05 实跑）**

| 参数 | `deepseek-v4-flash-dhwork` | `gpt-5.6-terra-dhwork` |
|---|---|---|
| `temperature` | ✅ 200 | ❌ **400 Unsupported parameter** |
| `top_p` | ✅ 200 | 未测（同类拒绝） |
| `top_k` | ❌ **400 `json: unknown field "top_k"`** | ❌ 同左 |
| `seed` | ✅ 200 | — |
| `presence_penalty` / `frequency_penalty` | ✅ 200 | — |
| `logprobs` / `top_logprobs` | ✅ 200 | — |
| `reasoning_effort`（`none`/`high`） | ✅ 200，`none` 时 reasoning_tokens=0 | ✅ 200 |

**usage 实测（推理模型会偷偷吃 token）**

| 模型 | prompt | completion | 其中 reasoning_tokens |
|---|---|---|---|
| `deepseek-v4-flash-dhwork` | 88 | 51 | **49** |
| `deepseek-v4-flash-dhwork` | 104 | 76 | **62** |
| `gpt-5.6-terra-dhwork` | 31 | 18 | 0 |

- **逐行要点**
  - `d.pop("name")`：`SamplingConfig` 里的 `name` 是我们自己的标签，混进请求体会被端点拒收。
  - `if v is not None`：`seed=None` 时**不要**把 `"seed": null` 发出去，一些端点对 null 会报参数错误。
  - `max_tokens=600`：不是随便写的。推理模型的 `max_tokens` 是**推理 + 正文**的共享预算，给小了正文直接是空字符串。
- **踩坑提示**
  1. **推理模型的 `max_tokens` 是共享预算**。本机实测：`max_tokens=48` 时 `deepseek-v4-flash-dhwork` 返回的 `content` 是 `''`，而 `usage.completion_tokens=51` 全花在 `reasoning_tokens` 上。**排查"模型返回空"时，第一个要看的就是 reasoning_tokens。**
  2. **`top_k` 在这套端点上不存在**。它是 Anthropic / vLLM 风格的字段，OpenAI 原生 API 也**没有** `top_k`。传了直接 400 `unknown field`。
  3. **推理模型（GPT-5.x 系）拒绝 `temperature`**。本机 `gpt-5.6-terra-dhwork` 传 `temperature` 返回 400 `Unsupported parameter: 'temperature' is not supported with this model.`。对这类模型，**"确定性"不再由 temperature 控制**，你能控的是 `reasoning_effort` 与提示词的约束强度。
  4. **别同时调 temperature 和 top_p**。两者叠加时它们的相互作用不直观，出问题无法归因。

> **零依赖版（不装 SDK，仅标准库）**：把 `{"model":..., "messages":..., "temperature":0}` 用 `json.dumps` 包好，`urllib.request.Request(url, data=..., headers={"Authorization":"Bearer "+TOKEN, "Content-Type":"application/json"})`，再 `json.load(urllib.request.urlopen(req))` 即可，返回结构完全一致（本文所有实测数据就是用它跑的）。

## 3 动手 / 联想（20 min）

- **动手任务（15 分钟）**：把上面的 `sampling.py` 拷到你本地任意一个 Python 工程里，然后写 3 行代码做一次对照实验：同一个抽取任务，分别用 `temperature=0` 和 `temperature=1.5` 各跑 5 次，把结果打到终端。目标不是"看谁对"，而是**亲眼看到 1.5 档会出现多少次格式跑偏**。
- **与我的工作结合**
  - **Android**：你可以把 `SamplingConfig` 直接翻译成 Kotlin 的 `enum class SamplingPreset`，在 Retrofit 的请求体里按业务选用。同一个 App 里，"OCR 结果纠错"走 `deterministic`，"AI 帮写朋友圈"走 `creative`——**一个 App 两套档位**是立刻就有的产品差异点。
  - **前端 / 小程序**：把档位做成后端的固定枚举（而不是让前端传 `temperature`）。前端传 `"temperature": 1.8` 是一件很危险的事——参数应该由服务端按场景锁定，这也顺手解决了一个安全问题。

## 5 明日预告与待复习（8 min）

- **明日主题**：流式输出（Streaming）——为什么"打字机效果"不是 UI 装饰，而是延迟工程。
- **待复习（3 条，今天必须记住）**
  1. `temperature` 是"胆量"：0 = 每步选最大（贪心），>1 分布变平更发散。
  2. `top_k` 是按**数量**截断，`top_p` 是按**累积概率**截断；**两者只调一个**。
  3. 推理模型的 `max_tokens` 是"推理 + 正文"共享预算——`content` 为空的第一个排查点是 `usage.completion_tokens_details.reasoning_tokens`。
- **一句话复盘**：最容易忘的是——**参数的可用性取决于端点和模型**，`temperature` 都不是"通用参数"，写代码时先探测再依赖。
