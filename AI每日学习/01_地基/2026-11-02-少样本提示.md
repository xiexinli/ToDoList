## 1 概念精讲（30 min）

**一句话定义**
少样本提示 = 在 `messages` 里放几条"输入 → 期望输出"的完整示例（通常 3～8 条），让模型在**推理时**模仿这个映射；模型权重一点没动，这叫**上下文学习（In-Context Learning, ICL）**。

**它解决什么问题 / 为什么现在必须懂**
1. 有些判断你**说不清规则但认得出来**。"这条留言算不算退款诉求"——你写十条 if 都比不上给三个例子。
2. 少样本是**格式约定**最省事的办法。你不需要用文字描述"输出要是 json、字段叫啥、单位是什么"，给两条示例就定死了。
3. 它是后面所有 Prompt 技巧（思维链、结构化输出、工具调用）的**共同套路**：**要什么，就先示范什么**。

**关键机制**

关键在于：few-shot **不是**拼接成一大段文本，而是复用上一讲的消息数组结构：

```
messages = [
  {"role": "system",    "content": "把用户留言分类到：退款、物流、账号、质量。只输出类别名。"},   ← 任务规则
  {"role": "user",      "content": "我的订单还没发货，等好久了"},                                ← 示例 1 输入
  {"role": "assistant", "content": "物流"},                                                    ← 示例 1 输出（这才是"标准答案"）
  {"role": "user",      "content": "想把这个退了，不想要了"},                                    ← 示例 2 输入
  {"role": "assistant", "content": "退款"},                                                    ← 示例 2 输出
  ...（再来 2 条）...
  {"role": "user",      "content": "包裹显示签收但我根本没收到"}                                 ← ★ 真正要分类的那条，必须最后
]
```

三个必须记住的结构事实：
1. **示例的"输出"要放在 `assistant` 角色里**，不是拼在 user 的文本里。这是少样本最容易被写错的地方——它决定了模型把这当成"我该模仿的格式"还是"用户随口提的一句话"。
2. **数组最后一条必须是 `user`**（要预测的那条）。如果最后一条是 `assistant`，模型会以为该它写下一句"用户说的话"，输出直接跑偏。
3. **示例按 user/assistant 交替排列**，这就是模型在预训练时见过的"对话"形态。

**为什么"举例"比"形容"有效**
- 示例同时携带了**标签空间**（原来只有 4 个类别可选）、**输出格式**（就一个词，不要解释）、**边界判据**（哪条留言算"物流"而不是"退款"）——三件事，一段文字描述要写两百字，两条示例就说完。
- 代价是**token**：每条示例都进上下文，还要**每一轮都重发一遍**（无状态 API 的特性，见 10-30 那一讲）。

**⚠️ 本机实测：强模型上"收益会消失"（这是今天最重要的一条）**

我用同一个模型（`deepseek-v4-flash-dhwork`，`temperature=0`）在 6 条真实工单留言上做了对照实验：

```
零样本（只给分类规则）：  正确 6/6
少样本（4 条示例）：      正确 6/6
```

**一模一样。** 两条结论：
1. 对**已经足够强、且任务足够简单**的模型，"少样本提升准确率"这件事**不成立**——模型靠 system 里那句规则就全做对了。
2. 但少样本**依然有价值**，只是价值不在"会不会分类"，而在**约束格式**：示例告诉它"只能输出类别名，不许带解释"。一旦你的输出要被程序解析，这个约束就是刚需。

> 所以正确的判断顺序是：**先跑零样本，看错在哪；错在"不会判断"才加示例，错在"格式不对"就用结构化输出（11-04 那讲）**。别一上来就堆示例——那是纯烧钱。

**常见误区**
1. **"示例越多越好。"** 不是。示例吃 token（每轮都重发），而且**噪声示例的伤害远大于数量带来的收益**——一条标错的示例足以把模型带偏。3～8 条、条条干净，远好过 20 条里混 3 条错的。
2. **"示例可以随手写。"** 示例 = 你亲手写给模型的"标准答案"。它抄的就是你给的。示例里凡是你不希望出现在生产输出里的东西（多余的解释、markdown 包裹、中英混杂），都会被忠实地学走。
3. **"示例顺序无所谓。"** 有所谓。模型对**靠后的示例**更敏感（recency），而且如果某些标签在示例里出现得特别多，模型会偏向那些标签（**majority label bias**）。工程做法：**每个标签至少一条，顺序打散，别把同一标签的示例挨着放**。

## 2 代码片段（40 min）

- **场景**：写一个**防偏置的 few-shot 组装器**——把示例定义成数据，自动做"覆盖检查 + 顺序打散 + 追加待分类项"，并顺手把"最后一条必须是 user"这个坑焊死在代码里。
- **依赖与版本**：`openai>=1.40.0`；端点用本机 DHwork 的 `https://www.dhcoder.net/llm-api/v1`。
- ⚠️ **诚实声明**：本机**未安装 openai SDK**。文中的对照结论（零样本 6/6 = 少样本 6/6）是用**等价的 `urllib` 请求**跑出来的；下面使用 SDK 的 `classify()` 片段**未在本机执行过**，需先 `pip install "openai>=1.40.0"`。

**① 组装器 `fewshot.py`**

```python
# fewshot.py —— 防偏置的 few-shot 组装器
# 设计目标：让"示例顺序错、标签失衡、最后一条不是 user"这三类坑从代码层面无法发生
import os
import random
from collections import Counter
from typing import List, Tuple, Dict, Any

from openai import OpenAI

client = OpenAI(api_key=os.environ["DHWORK_TOKEN"],
                base_url="https://www.dhcoder.net/llm-api/v1")

Example = Tuple[str, str]          # (输入, 期望输出)
Message = Dict[str, str]


class FewShotBuilder:
    def __init__(self, system_prompt: str, labels: List[str],
                 examples: List[Example], shuffle_seed: int = 42):
        self.system_prompt = system_prompt
        self.labels = labels
        self.examples = examples
        self.shuffle_seed = shuffle_seed
        self._validate()

    def _validate(self) -> None:
        """★ 上线前必须跑的检查：标签覆盖 + 无重复输入。"""
        seen = Counter(label for _, label in self.examples)
        missing = [l for l in self.labels if seen[l] == 0]
        if missing:
            # 缺标签 = 模型永远学不会该标签，是少数类准确率崩塌的元凶
            raise ValueError(f"示例缺少这些标签，会造成多数类偏置: {missing}")
        inputs = [t for t, _ in self.examples]
        if len(inputs) != len(set(inputs)):
            raise ValueError("存在完全相同的示例输入，重复示例会放大偏置")

    def build(self, query: str) -> List[Message]:
        """生成最终 messages：system + 打散后的示例 + 待分类项。"""
        ex = self.examples[:]
        random.Random(self.shuffle_seed).shuffle(ex)   # ★ 固定 seed：打散但不破坏可复现性

        msgs: List[Message] = [{"role": "system", "content": self.system_prompt}]
        for text, label in ex:
            msgs.append({"role": "user", "content": text})
            msgs.append({"role": "assistant", "content": label})   # ★ 示例答案必须是 assistant
        msgs.append({"role": "user", "content": query})            # ★ 最后一条必须是 user
        return msgs


SYSTEM = "把用户留言分类到以下四类之一：退款、物流、账号、质量。只输出类别名，不要任何解释。"
LABELS = ["退款", "物流", "账号", "质量"]
EXAMPLES: List[Example] = [
    ("我的订单还没发货，等好久了", "物流"),
    ("想把这个退了，不想要了", "退款"),
    ("密码忘了登不上", "账号"),
    ("衣服线头很多，做工不好", "质量"),
    ("包裹显示签收但我根本没收到", "物流"),   # 同一标签来两条也没关系，会打散
]

builder = FewShotBuilder(SYSTEM, LABELS, EXAMPLES)


def classify(text: str, use_examples: bool = True) -> str:
    """use_examples=False 即零样本——用来做 A/B 对照。"""
    msgs = (builder.build(text) if use_examples
            else [{"role": "system", "content": SYSTEM},
                  {"role": "user", "content": text}])
    resp = client.chat.completions.create(
        model="deepseek-v4-flash-dhwork",
        messages=msgs,
        temperature=0,
        max_tokens=600,          # 推理模型：预算要给足，否则 content 会是空串
    )
    return (resp.choices[0].message.content or "").strip()


if __name__ == "__main__":
    tests = [
        ("快递三天没动了，一直显示已揽收", "物流"),
        ("收到的杯子是碎的，有裂痕", "质量"),
        ("我要申请退款，订单号12345", "退款"),
        ("登录一直提示验证码错误，进不去", "账号"),
        ("包裹显示签收但我根本没收到", "物流"),
        ("这个颜色和图片差太多了，我想退钱", "退款"),
    ]
    for use_ex in (False, True):
        hits = []
        for text, gold in tests:
            pred = classify(text, use_ex)
            hits.append(pred == gold)
        name = "少样本" if use_ex else "零样本"
        print(f"{name}: 正确 {sum(hits)}/{len(tests)}")
```

**本机实测输出（2026-11-05 补写时实跑，非杜撰）**

```
零样本: 正确 6/6
少样本: 正确 6/6
```

**② 一个能看出差别的"边界样本"实验（建议你自己跑）**

上面 6 条太"干净"，所以零样本全对。把测试集换成**边界模糊**的留言，差别才会出现：

```python
    tests = [
        ("包裹一直不更新，我能不能退款？", "物流"),   # 同时含"物流"和"退款"两个关键词
        ("收到的货有质量问题，我要退钱", "质量"),      # 质检问题 + 退款动作
        ("账号被盗了，里面还有余额", "账号"),
        ("这个不是我订的那款，想换", "退款"),
    ]
```

**逐行要点**
- `_validate()` 里的"标签覆盖检查"：**缺标签 = 模型永远学不会那个类**。这是 few-shot 类任务里少数类 recall 崩掉的第一元凶，而且不报错、只是悄无声息地变差。
- `random.Random(seed).shuffle()`：**局部 Random 实例**，不污染全局随机状态。示例必须打散（避免顺序偏置），但打散方式必须可复现（否则你调不出问题）。
- `max_tokens=600`：本机模型是推理模型，`max_tokens` 是"推理 + 正文"的共享预算，给 48 时 `content` 会直接是空串。
- **踩坑提示**
  1. **示例的输出行必须是 `assistant` 角色**。把它拼进 user 文本里，模型会把"标准答案"当成用户提供的背景，输出格式全乱。
  2. **最后一条必须是 `user`**。结尾是 `assistant` 会让模型继续扮演"用户"，答非所问。
  3. **不要同时用 few-shot 和"输出格式说明"打架**。示例里输出了 Markdown 代码块、又在 system 里说"只输出纯文本"，模型会摇摆。**示例本身就等价于格式说明**，二者必须一致。
  4. **`temperature=0` 下少样本仍可能不稳定**：示例的**顺序**一变，结果就可能变。所以顺序要固定 seed，别随机。

## 3 动手 / 联想（20 min）

- **动手任务（15 分钟）**：从你手头挑一个**现在用 if-else 写**的判断逻辑（工单分类、日志归因、内容审核标签、表单字段识别——随便哪个都行）。做三步：
  1. 写 1 句 system 规则 + 直接问模型（**零样本**），在 10 条真实数据上记录正确率；
  2. 再把规则里的 if-else 分支各翻译成 1 条示例（**每类至少一条**），再跑一次；
  3. 对比两次：**如果正确率没涨，那这个任务就不该用 few-shot，该用规则**——省下的 token 和延迟都是利润。
- **与我的工作结合**
  - **Android**：把"用户输入 → App 内意图"的映射交给 few-shot 是最划算的。比如一个记账 App，用户说"昨天晚上吃饭花了 180"，要变成 `{"type":"餐饮","amount":180,"date":"昨天"}`——你写正则要写几十条，写 4 条示例就基本够用，而且新表达方式能自动泛化。
  - **前端 / 小程序**：表单的"自然语言填写"（用户对着输入框说"我要订下周三下午两点的会议室"）天然适合 few-shot；注意把示例集放在**服务端**而不是打包进前端，示例是 prompt 资产，改它不该发版。

- **待复习（3 条，今天必须记住）**
  1. 示例的**输出要放进 `assistant` 角色**，数组**最后一条必须是 `user`**。
  2. few-shot 的真实收益在**格式与边界约束**，不在"让强模型变聪明"——**先跑零样本再决定加不加**。
  3. 示例集必须做**标签覆盖检查 + 顺序打散（固定 seed）**，否则会引入多数类偏置。
- **一句话复盘**：最容易忘的是——**few-shot 是花钱买"说不清的规则"**；规则说得清的场景，用规则更便宜也更稳。
