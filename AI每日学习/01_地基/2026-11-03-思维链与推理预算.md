## 1 概念精讲（30 min）

**一句话定义**
思维链（CoT）= 让模型在给出最终答案**之前**，先输出一串中间推理步骤。它把"一次算完"变成"边写边算"——因为 Transformer 每生成一个 token 才有一次计算机会，**写出来的字就是它的草稿纸**。

**它解决什么问题 / 为什么现在必须懂**
1. 多步推理（算术、多跳问答、条件判断）上，"直接给答案"的错误率显著更高。
2. 但 2026 年的现实是：**主流模型已经是"推理模型"了**——它们**不管你说不说，内部都会先想一遍**。所以今天真正的工程问题不再是"要不要 CoT"，而是"**买多少推理预算**"。
3. 推理 token **照样计费、照样占 `max_tokens`**。不搞清这件事，你的成本和"返回空内容"的诡异 bug 都会从这里来。

**关键机制**

```
① 传统模型（非推理）
   prompt ──► [直接输出答案]
   需要 CoT 时，靠提示词"逼"它写草稿：
     - zero-shot CoT：在 prompt 末尾加一句"Let's think step by step"（中文："请一步一步思考"）
     - few-shot CoT：示例里给出"带推理过程的标准答案"，让它照着写
   结构：prompt ──► 推理过程 + 答案（混在一起输出）

② 推理模型（本机这两个模型都是）
   prompt ──► [内部草稿：reasoning_content] ──► [最终答案：content]
                     ↑ 你看不见（除非流式里有 delta.reasoning_content）
                     ↑ 但【照样算 token、照样算钱】
   控制方式不再是"写 CoT 提示词"，而是参数：
     reasoning_effort: none / low / medium / high ...
```

**本机实测的两个反直觉结论（2026-11-05 实跑，非杜撰）**

**实验 A：显式 CoT 在这套模型上是冗余的**

```
题目：4 道多跳算术题（全班人数、打折、时间推算…），模型 deepseek-v4-flash-dhwork，temperature=0
  直接回答（"只输出最终答案，不要过程"）：  正确 4/4
  先推理（"请一步一步推理，最后用『答案：X』"）：正确 4/4
```

一模一样。原因很直接：**它就是推理模型**，你让不让你都拦不住它先想一遍——`usage.completion_tokens_details.reasoning_tokens` 里躺着几十上百个 token 的"内部草稿"。**对推理模型手写 CoT（尤其是 few-shot CoT）基本是白烧 token。**

**实验 B：推理预算开满，不一定买到准确率（今天最重要的一张表）**

```
8 道多步推理题，模型 gpt-5.6-terra-dhwork
reasoning_effort=none :  正确 8/8   reasoning_tokens 合计 = 0     耗时 22s
reasoning_effort=high :  正确 8/8   reasoning_tokens 合计 = 303   耗时 36s
```

**准确率完全相同，`high` 档多花了 303 个推理 token 和 +64% 的墙钟时间。**

这不是说 CoT/推理预算没用，而是说：**它是"按需购买"的。** 题太简单时，你花的钱买到的只是延迟。正确的姿势是——**在你自己的真实数据集上，跑一次档位对照，再决定默认档**（今天的动手任务就是干这个）。

**什么时候推理预算真的值钱**
- ✅ 值得：多跳检索问答、SQL 生成、代码调试、有相互约束条件的规划、需要"算一步看一步"的题。
- ❌ 不值得：分类、抽取、改写、翻译、格式转换、简单单步计算——**这些用 `none`/`low`**。

**常见误区**
1. **"CoT 一定提升效果。"** 不一定。推理模型上收益趋零（实验 A），简单任务上纯亏（实验 B）。而且小模型上长推理链还可能**越推越错**（overthinking）。
2. **"模型的思考过程可以给用户看。"** 可以看，但必须**明确标注**。思考过程里会有废话、自我纠错、甚至中途的错答案——把 `reasoning_content` 当"解释"直接展示给用户，是客服场景的常见翻车点。产品上通常**默认折叠**。
3. **"思维链能替代工具。"** 不能。CoT 提升的是"推理可靠性"，不是"事实准确性"。**要精确的数字/汇率/库存，必须走工具**（明天讲），CoT 只是让模型知道"我该去查"。
4. **"`max_tokens` 只算正文。"** 错，这是最坑的一条。`max_tokens` 是"**推理 + 正文**"的共享预算。推理档开高后，留给正文的空间被吃掉，你会看到**返回空字符串但 `finish_reason="stop"`** 这种看似无缘无故的现象。

## 2 代码片段（40 min）

- **场景**：写一个**"推理档位对照器"**——同一个数据集，用不同 `reasoning_effort` 各跑一遍，输出"准确率 / 推理 token / 墙钟时间"三列，让你用数据决定默认档，并在代码里**把推理过程与答案强制分离**。
- **依赖与版本**：`openai>=1.40.0`；端点用本机 DHwork 的 `https://www.dhcoder.net/llm-api/v1`。
- ⚠️ **诚实声明**：本机**未安装 openai SDK**。文中两组实测数据（直答 vs CoT、effort=none vs high）是用**等价的 `urllib` 请求**跑出来的；下面使用 SDK 的片段**未在本机执行过**，需先 `pip install "openai>=1.40.0"`。

**① 两段式输出：推理归推理、答案归答案 `cot.py`**

```python
# cot.py —— 推理档位对照器 + 两段式输出解析
# 核心思想：绝不让"最终答案"和"推理过程"混在同一个字段里被下游解析
import os
import re
import time
from typing import List, Tuple, Optional

from openai import OpenAI

client = OpenAI(api_key=os.environ["DHWORK_TOKEN"],
                base_url="https://www.dhcoder.net/llm-api/v1")

# ★ 用标签把两段分开：模型负责"想"，代码负责"取"
PROMPT_TEMPLATE = """{question}

请先在 <thinking> 里分析，然后在 <answer> 里只写最终结果的数字。
格式严格如下（标签必须出现）：
<thinking>你的推理过程</thinking>
<answer>数字</answer>"""

_ANS = re.compile(r"<answer>\s*(.*?)\s*</answer>", re.S)


def answer(question: str, effort: str = "none",
           model: str = "gpt-5.6-terra-dhwork") -> Tuple[Optional[str], int, float]:
    """返回 (答案, reasoning_tokens, 墙钟秒数)。"""
    t0 = time.time()
    resp = client.chat.completions.create(
        model=model,
        messages=[{"role": "user", "content": PROMPT_TEMPLATE.format(question=question)}],
        reasoning_effort=effort,     # ★ 今天的核心旋钮
        max_tokens=2000,             # ★ 必须放宽：它要同时装下推理和正文
    )
    cost = time.time() - t0
    text = resp.choices[0].message.content or ""
    # 从 <answer> 里取值——取不到就返回 None，交给上层重试/兜底
    m = _ANS.search(text)
    details = getattr(resp.usage, "completion_tokens_details", None)
    rtok = getattr(details, "reasoning_tokens", 0) or 0
    return (m.group(1) if m else None), rtok, cost


QUESTIONS: List[Tuple[str, str]] = [
    ("一个数加上17再乘以3等于96，这个数是多少？", "15"),
    ("商店打7折后是84元，原价多少元？", "120"),
    ("三人分100元，甲比乙多10，乙比丙多6，则甲多少元？", "42"),
    ("从1加到20等于多少？", "210"),
    ("正方体切成8个相同小正方体，表面积变为原来的几倍？", "2"),
    ("5台机器5分钟生产5个零件，100台机器生产100个零件要几分钟？", "5"),
    ("10把椅子编号1-10排一排，移走所有偶数号，还剩几把？", "5"),
    ("一根绳子对折三次后剪一刀，会变成几段？", "9"),
]


def run(effort: str) -> None:
    hit = 0
    rtok_total = 0
    t0 = time.time()
    for q, gold in QUESTIONS:
        got, rtok, _ = answer(q, effort=effort)
        rtok_total += rtok
        # 从数字里比：避免 "42元" / "42" 这类无关差异
        hit += bool(got) and re.findall(r"\d+", got)[-1] == gold
    print(f"reasoning_effort={effort:5}  正确 {hit}/{len(QUESTIONS)}"
          f"  reasoning_tokens合计={rtok_total:4}  总耗时={time.time()-t0:.0f}s")


if __name__ == "__main__":
    for eff in ("none", "high"):
        run(eff)
```

**本机实测输出（2026-11-05 补写时实跑，非杜撰）**

```
reasoning_effort=none   正确 8/8  reasoning_tokens合计=  0  总耗时=22s
reasoning_effort=high   正确 8/8  reasoning_tokens合计=303  总耗时=36s
```

**② 如果你想看模型"到底想了什么"（调试用，不要进生产）**

```python
# peek_reasoning.py —— 流式取出内部推理过程，仅用于排查"它为什么答错"
stream = client.chat.completions.create(
    model="deepseek-v4-flash-dhwork",
    messages=[{"role": "user", "content": "书店打8折，我花了64元，原价多少？"}],
    stream=True,
    max_tokens=900,
)
for chunk in stream:
    if not chunk.choices:
        continue
    d = chunk.choices[0].delta
    if getattr(d, "reasoning_content", None):        # 内部草稿
        print(d.reasoning_content, end="", flush=True)
    elif d.content:                                   # 最终答案
        print("\n--- 答案 ---", d.content, end="", flush=True)
```

- **逐行要点**
  - `<thinking>` / `<answer>` 标签对：**用标签把"给机器解析的部分"圈出来**。这是防止"模型在推理里也写了数字、你把错的解析走了"的标准做法。（更彻底的做法是结构化输出，见明天那一讲。）
  - `getattr(details, "reasoning_tokens", 0) or 0`：不是所有端点都返回这个字段，取不到时**不能崩，也不能当成"没推理"**——要按 `None` 处理。
  - `max_tokens=2000`：本讲反复强调。推理档越高，这个值越要给足。
  - `re.findall(r"\d+", got)[-1]`：比对时取**最后一个数字**，避免"答案是 42 元"这种带单位的输出被判错。
- **踩坑提示**
  1. **`finish_reason="stop"` 也可能内容为空**。原因就是 `max_tokens` 被推理吃光。排查顺序永远是：先看 `reasoning_tokens`，再看正文。
  2. **不同模型的 `reasoning_effort` 取值不一样**。本机实测 `none` / `high` 都被接受；但本机 `gpt-5.6-terra-dhwork` **连 `temperature` 都不接受**（400 `Unsupported parameter`）——**别把参数兼容性当成理所当然**，接入前先探测。
  3. **不要用 few-shot CoT 去"教"推理模型**。给推理模型塞"带推理过程的示例"，是在为一个已经在做的事付双份钱（示例占 prompt token + 它自己还要再想一遍）。
  4. **CoT 不是给你省工具的**。它不会让模型知道今天的汇率，只会让它知道"我该去查汇率"——那需要工具调用。

## 5 明日预告与待复习（8 min）

- **明日主题**：结构化输出（JSON Schema / 受约束解码）——以及本机端点一个**很坑的实测发现**：它接受 `json_schema` 参数并返回 200，但**根本不强制**执行。
- **待复习（3 条，今天必须记住）**
  1. 对**推理模型**来说，手写 CoT 提示基本是冗余的——它内部一定会先想；控制方式改成了 **`reasoning_effort`**。
  2. **推理预算要按任务买**：本机实测 `high` 档在简单题集上 = 8/8 同样正确 + 303 token + 64% 时间。
  3. **`max_tokens` 是"推理 + 正文"共享预算**；`content` 为空但 `finish_reason="stop"` 时，第一个排查点是 `reasoning_tokens`。
- **一句话复盘**：最容易忘的是——**CoT 是"用 token 换推理可靠度"的交易**，不是免费的能力开关；交易划不划算，只能在自己的数据上量。
