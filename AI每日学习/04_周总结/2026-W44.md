## 2 一周一句话（每讲压成一句，用来回忆）

1. **Token 与上下文窗口**：模型按 token 计价、上下文窗口是"输入 + 输出"的共享预算，超了要自己裁。
2. **消息结构（Roles）**：你发的不是一段文本，而是一个**带角色的数组**；`system` 是你唯一能"钉规则"的地方，而且**角色名写错不会报错、只会静默失效**。
3. **采样参数**：`temperature` 是"胆量"（0 = 贪心），`top_k` 按数量截断、`top_p` 按累积概率截断且**两者只调一个**。
4. **流式输出**：优化的是 **TTFT / 感知延迟**而非总耗时；字段从 `message.content` 变成增量的 `delta.content`，且**结束判断不能只靠 `[DONE]`**。

## 3 本周实测数据（自己的机器上跑出来的，不是抄的）

这些数字是本周最有价值的资产——面试或写方案时，**能说出自己实测数字的人和只会背概念的人，是两类人**。

| 实测项 | 结果 |
|---|---|
| 消息角色名大写 `System` | HTTP 200 但**约束静默失效**（最危险的坑） |
| `temperature=0` 可复现性 | 服务端不保证；工程上要"低温度 + 输出校验" |
| `top_k` 参数 | ❌ 400 `json: unknown field "top_k"`（该端点不支持） |
| `temperature` 传给 `gpt-5.6-terra-dhwork` | ❌ 400 `Unsupported parameter`（推理模型不收） |
| 推理模型的 `max_tokens` | 是"推理 + 正文"共享预算；给 48 时 `content` 直接是**空串** |
| 同一问题：流式 vs 非流式 | TTFT **2.04s** vs 首字节 **3.56s**（总耗时都约 3s） |
| 流式的结束标记 | 41 行 chunk 里**没有 `[DONE]`**，也没有 usage 块 |

## 5 本周暴露的三个薄弱点（下周针对性补）

1. **参数兼容性靠猜**。本周连续踩了 `top_k`、`temperature` 两个"参数不被接受"的坑 → **结论：接入任何端点前先跑一个参数探测脚本**，把兼容性表落成文件（已在 10-31 那讲给出实测表模板）。
2. **"能不能复现"没有工程手段**。目前只有"设低温度"这一个动作，缺"输出校验 + 记录 seed/模型版本"的完整链路 → W2 结构化输出会补上校验那一环。
3. **成本意识刚刚建立**。第一次意识到"推理 token 也计费、也占预算"，但还没有形成"每次改动都量一下 token/延迟"的习惯 → 从 W2 起，每个动手任务都要记录一个数字。
