# aidlc-workshop 中的 AI 开发概念拆解

> 目的：把 `aidlc-workshop` Skill 中涉及的 AI、AI 应用工程和流程治理概念拆开，便于按层次学习。
>
> 说明：这份文档以该 Skill 的内容为范围，不把它当作某个具体业务系统的设计；示例中的订单助手、客服助手均为学习用抽象示例。

---

## 1. 先看全局：AI 应用开发不是“调用一次模型”

一个可交付的 AI 应用通常包含以下链路：

```text
业务问题
  ↓
需求与验收标准（EARS / AC）
  ↓
架构边界（lib / adapters / 外壳）
  ↓
核心逻辑与测试（TDD）
  ↓
LLM、工具、MCP 和外部服务接入
  ↓
Fake → Real → Live 分层验证
  ↓
Guardrail 与人工审批
  ↓
CI、追溯、演示与交付
  ↓
脚手架和 Skill 复用
```

### 三类概念

| 类别 | 关注的问题 | 主要概念 |
|---|---|---|
| AI 概念 | 模型如何理解、决策和行动 | LLM、Agent、工具调用、MCP、编排器、Guardrail |
| 软件工程概念 | 系统如何构建、测试和复用 | TDD、测试契约、Web MVP、分层、拓扑、CI、脚手架 |
| 流程治理概念 | 需求如何确认、风险如何控制、证据如何留存 | AI-DLC、EARS、AC、追溯、人工门禁、interactive/yolo |

# 第一部分：流程治理概念

## 2. AI-DLC：AI Development Lifecycle

### 是什么

AI-DLC 是面向 AI 应用的开发生命周期。它把 AI 项目从“模型实验”变成一套可规划、可测试、可审批、可交付的工程流程。

### 文件中的位置

- `SKILL.md`：整体流程
- `stages/spec.md`：Inception
- `stages/tdd.md`：Construction
- `stages/demo.md`：收口与演示

### 解决什么问题

- 需求模糊，无法判断是否完成；
- 只证明模型能回答，没有证明系统可交付；
- 测试依赖真实服务，慢且不可复现；
- 模型有不确定性，却没有明确边界；
- 每个项目都重复搭建相同流程。

### 简单例子

“做一个订单查询助手”不能只写一个 Prompt，还要明确：

1. 用户可以提供什么输入；
2. 何时调用订单工具；
3. 订单不存在时如何回答；
4. 哪些字段不能泄露；
5. 退款等写操作是否需要人工审批；
6. 如何用测试和真实验证证明完成。

### 学习重点

先掌握完整链路：

```text
问题 → 需求 → AC → 测试 → 实现 → 真实验证 → 交付证据
```

## 3. Inception、Construction、收口

| 阶段 | 主要问题 | 典型产物 |
|---|---|---|
| Inception | 做什么、边界是什么、如何验收 | `questions.md`、`requirements.md`、`design.md`、`tasks.md` |
| Construction | 如何实现并证明每条需求 | 代码、测试、适配器、`traceability.md` |
| 收口 | 能否在目标条件下运行、如何演示 | `DEMO.md`、测试报告、Live Eval、复盘 |

### 与普通软件开发的对应关系

- Inception ≈ 需求分析与方案设计；
- Construction ≈ 开发、测试与集成；
- 收口 ≈ 验收、演示、发布准备。

### 为什么 AI 项目特别需要阶段化

AI 项目容易出现“先接模型、后补规则”的问题。阶段化要求先明确：

- 模型负责什么；
- 程序负责什么；
- 哪些动作必须经过人；
- 什么结果才算通过。

## 4. EARS：可验证的需求写法

### 是什么

EARS（Easy Approach to Requirements Syntax）把自然语言需求写成有触发条件、有主体、有可观察响应的句子。

### 五种基本句型

| 类型 | 句型 | 用途 |
|---|---|---|
| Ubiquitous | `THE 系统 SHALL 响应` | 永远成立的规则 |
| Event-driven | `WHEN 事件 THE 系统 SHALL 响应` | 用户操作或输入到达 |
| State-driven | `WHILE 状态 THE 系统 SHALL 响应` | 某种状态持续期间 |
| Unwanted | `IF 异常 THEN THE 系统 SHALL 响应` | 错误、缺失、违规 |
| Optional | `WHERE 特性存在 THE 系统 SHALL 响应` | 可选能力 |

### 示例

模糊需求：

```text
AI 应该智能地查询订单。
```

EARS 写法：

```text
WHEN 用户提供有效订单号 THE 订单助手 SHALL 调用订单查询工具。
IF 订单查询工具返回 not_found THEN THE 订单助手 SHALL 提示未找到订单且不得编造订单状态。
IF 用户未提供订单号 THEN THE 订单助手 SHALL 请求补充订单号。
```

### 合格判据

一条 EARS 最好满足：

- 只有一个主要 SHALL 响应；
- 能直接设计测试断言；
- 有具体字段、数字或枚举；
- 主体明确；
- 不把实现细节写进需求。

### 与其他概念的关系

```text
EARS → AC → 测试 → 实现 → Demo / Eval
```

---

## 5. AC：Acceptance Criteria，验收标准

### 是什么

AC 是判断一项需求是否完成的具体条件。它应该能得到明确的 PASS 或 FAIL。

### 示例

```text
AC-01：输入有效订单号时，系统返回订单状态。
AC-02：订单不存在时，系统提示未找到且不编造状态。
AC-03：订单服务超时时，系统给出失败提示。
AC-04：涉及修改订单的操作必须先经过确认。
```

### AC ID 的作用

Skill 要求使用稳定编号，例如 `AC-01`，并贯穿：

```text
requirements.md
→ tasks.md
→ 测试名称
→ 实现注释
→ traceability.md
→ DEMO.md
```

这样可以知道某条业务要求到底有没有被测试和实现。

### 优先级

- **P0**：演示或交付必须通过；
- **P1**：重要加料，时间不足时可暂缓；
- **P2**：后续增强。

## 6. 需求追溯：从需求追到代码和证据

### 是什么

需求追溯是建立以下对应关系：

```text
任务卡
  → EARS
  → AC
  → 任务
  → 测试
  → 实现
  → Demo / Live Eval
```

### 解决什么问题

- 需求变更后，知道哪些代码和测试受影响；
- 测试通过后，确认它确实覆盖了业务要求；
- Demo 不只是“演示好看的功能”，而是对应具体 AC；
- 出现问题时能追溯遗漏发生在哪一层。

### 典型表格

| AC | 测试 | 实现 | 证据 | 状态 |
|---|---|---|---|---|
| AC-01 | `test_ac_01_query_success` | `queryOrder()` | Demo-01 | PASS |
| AC-02 | `test_ac_02_not_found` | `handleNotFound()` | Demo-02 | PASS |

## 7. Human-in-the-loop：人工参与关键决策

### 是什么

Human-in-the-loop（HITL）指在 AI 流程的高风险节点，让人进行确认、修正、批准或终止。

### 适合人工介入的场景

- 修改外部数据；
- 删除、退款、转账、权限变更；
- 模型置信度低；
- 工具返回异常；
- 结果对用户影响重大；
- 操作不可逆。

### 示例

```text
用户请求退款
  → AI 识别意图
  → 查询订单是否满足退款条件
  → 生成退款草稿
  → 人工确认
  → 才允许调用退款工具
```

### 与 Guardrail 的关系

HITL 是 Guardrail 的一种实现方式，但 Guardrail 还包括：

- 输入校验；
- 工具白名单；
- 权限控制；
- 输出脱敏；
- 固定拒答；
- 失败时停止。

---

## 8. interactive 与 yolo

### interactive

交互式模式。AI 在关键节点停下来，让人查看计划、确认需求或批准操作。

适合：

- 需求不清；
- 高风险工具；
- 不可逆操作；
- 需要共同决策的项目。

### yolo

高自主执行模式。AI 在预先授权的范围内连续推进，减少逐步确认。

适合：

- 低风险；
- 可逆操作；
- 规则清楚；
- 重复性高；
- 已有充分测试和日志。

### 关键原则

```text
yolo ≠ 没有安全边界
```

即使自动模式，也应记录假设、尊重权限、遇到高风险操作时暂停。

# 第二部分：AI 核心概念

## 9. LLM：大语言模型

### 是什么

LLM（Large Language Model）是理解和生成自然语言的模型。它擅长：

- 问答；
- 总结；
- 分类；
- 信息抽取；
- 意图识别；
- 生成结构化输出；
- 规划工具调用。

### 不是什么

LLM 不是：

- 可靠数据库；
- 权限系统；
- 业务规则引擎；
- 自动正确的事实来源。

### 示例

用户输入：

```text
我的订单 A123 怎么还没到？
```

LLM 可以识别：

```json
{
  "intent": "query_order_status",
  "order_id": "A123"
}
```

但是否真的查询订单，应由程序和工具完成。

### 学习重点

把 LLM 当作“概率型语言组件”，不要把它当成完全确定性的函数。需要给它配合：

- 结构化输入输出；
- 工具；
- Guardrail；
- 测试；
- 失败和超时处理。

---

## 10. Agent：智能体

### 是什么

Agent 是以 LLM 为核心、能够理解目标、选择步骤、调用工具、读取结果并继续完成任务的系统单元。

一个 Agent 通常包含：

```text
目标 + 上下文 + LLM + 工具 + 状态 + 规则 + 停止条件
```

### LLM 与 Agent 的区别

| 概念 | 主要能力 |
|---|---|
| LLM | 理解和生成文本 |
| Agent | 围绕目标完成多步任务 |

LLM 可以没有工具；Agent 通常需要工具、状态和执行规则。

### 示例

```text
用户：查询 A123，并告诉我是否需要联系客服

Agent：
1. 识别订单号和意图；
2. 调用订单工具；
3. 读取物流结果；
4. 判断是否异常；
5. 生成解释和建议。
```

### 初学建议

不要从“万能 Agent”开始。先做：

```text
一个目标 → 一个只读工具 → 一个结构化结果
```

## 11. 工具调用：让模型从“会说”变成“能做”

### 是什么

工具调用（Tool Calling / Function Calling）是模型输出结构化调用请求，由程序真正执行工具，再把结果交回模型。

### 基本流程

```text
用户问题
  → LLM 判断需要工具
  → 输出工具名和参数
  → 程序校验参数并执行
  → 工具返回结果
  → LLM 组织最终回答
```

### 示例

模型请求：

```json
{
  "tool": "get_order_status",
  "arguments": { "order_id": "A123" }
}
```

工具返回：

```json
{
  "ok": true,
  "order_id": "A123",
  "status": "shipped"
}
```

### 工具设计原则

1. 参数少且明确；
2. 输入输出结构化；
3. 成功与失败格式稳定；
4. 只读与写操作分开；
5. 权限判断不能只交给模型；
6. 每个工具都有 Fake 和契约测试。

---

## 12. MCP：Model Context Protocol

### 是什么

MCP 是一种标准化接入模型上下文、工具和外部资源的协议思路。

可以简单理解为：

```text
工具调用 = 具体调用某个能力
MCP = 以统一方式描述、发现和连接这些能力
```

### 它解决的问题

没有统一接入方式时，不同模型、客户端和业务系统之间会出现大量重复集成代码。MCP 的目标是让工具和上下文更容易复用。

### 工具调用与 MCP 的区别

| 概念 | 关注点 |
|---|---|
| 工具调用 | 模型如何请求执行某个动作 |
| MCP | 工具、资源和上下文如何标准化暴露和接入 |

### 学习顺序

1. 先写本地函数工具；
2. 设计清楚输入、输出、错误和权限；
3. 写 Fake 和契约测试；
4. 再学习如何用 MCP 暴露工具。

---

## 13. 编排器：协调 Agent、工具和流程

### 是什么

编排器（Orchestrator）负责安排任务顺序、管理状态、处理失败、决定何时调用工具、何时暂停审批以及何时结束流程。

### 示例

```text
校验输入
  → 查询订单
  → 判断业务规则
  → 生成建议
  → 请求人工审批
  → 执行写操作
  → 记录结果
```

### Agent 与编排器的区别

| 概念 | 类比 |
|---|---|
| Agent | 负责完成一项智能任务的执行者 |
| 编排器 | 负责分配步骤和控制全局流程的协调者 |

### 设计建议

确定性流程优先写在程序中：

```text
校验 → 查询 → 判断 → 审批 → 执行 → 记录
```

只把适合语言理解、总结、分类和生成的部分交给 LLM。

---

## 14. Guardrail：AI 系统的护栏

### 是什么

Guardrail 是限制 AI 输入、输出、工具和行动范围的规则与机制。

### 四类 Guardrail

| 类型 | 示例 |
|---|---|
| 输入护栏 | 缺少必要参数时追问；检测敏感信息 |
| 模型护栏 | 输出必须符合 JSON 或固定格式 |
| 工具护栏 | 工具白名单、参数范围、权限校验 |
| 流程护栏 | 写操作必须审批；失败后停止 |

### 示例

```text
IF 工具返回 not_found
THEN 系统 SHALL 说明未找到，且不得推测具体状态。
```

### 重要原则

不要只靠 Prompt 保护高风险操作。权限、金额计算、审批和状态变更等确定性规则应放在可测试代码中。

---

## 15. Fake、Real、Live：真实性逐步提升

| 层级 | 用途 | 优点 | 风险 |
|---|---|---|---|
| Fake | 单元测试和离线演示 | 快、稳定、可重复 | 可能与真实实现不同 |
| Real | 真实 SDK 或受控测试环境 | 验证集成、协议和配置 | 环境复杂、不稳定 |
| Live | 接近真实用户和目标环境 | 验证整体可用性 | 成本、权限和副作用较高 |

### 示例

```text
Fake：固定返回 shipped
Real：调用测试环境订单服务
Live：在授权条件下走完整真实用户路径
```

### 重要区别

```text
Fake 通过 ≠ Real 通过
Real 通过 ≠ Live 已验证
Live 可用 ≠ 可以取消 Guardrail
```

### 推荐顺序

```text
Fake 测试
  → Real 集成验证
  → 受控 Live 验证
  → 扩大发布范围
```

## 16. 合成样本：可控、可重复的测试数据

### 是什么

合成样本（Synthetic Samples）是人工设计或程序生成的测试输入、工具返回、对话和边界数据。

### 为什么需要

真实数据可能：

- 包含隐私；
- 难以覆盖罕见错误；
- 不稳定；
- 获取成本高；
- 不适合频繁跑 CI。

### 示例

```json
{
  "name": "订单不存在",
  "input": "查询 X999",
  "tool_result": { "error": "not_found" },
  "expected": "提示未找到，不得编造状态"
}
```

### 设计方法

每条 AC 至少设计：

1. 一个正常样本；
2. 一个边界样本；
3. 一个异常样本。

## 17. Live Eval：真实条件下的 AI 评估

### 是什么

Live Eval 是在真实模型、真实 SDK、真实或接近真实的外部服务和真实运行条件下，对 AI 系统进行评估。

### 不只看回答文本

还应检查：

- 是否调用正确工具；
- 工具参数是否正确；
- 是否遵守 Guardrail；
- 是否在失败时安全降级；
- 是否出现幻觉或虚假承诺；
- 是否满足 AC。

### 评估记录示例

```markdown
场景：订单不存在
输入：查询 X999
实际工具调用：get_order_status({id: "X999"})
实际结果：not_found
是否满足 AC-02：是
是否触发护栏：是
问题：无
```

### 与普通单元测试的区别

- 单元测试追求快、稳定、可重复；
- Live Eval 追求接近真实，允许存在环境波动；
- Live Eval 不应替代单元测试。

---

## 18. SDK 探针：先验证依赖，再开发复杂功能

### 是什么

SDK Probe 是一个极小的验证程序，用于确认 SDK、认证、网络、工具协议或模型调用是否真的可用。

### 探针通常做什么

```text
加载配置
  → 发送最小请求
  → 检查返回
  → 输出版本、耗时和错误类型
```

### 解决什么问题

当复杂 Agent 失败时，问题可能来自：

- SDK 版本；
- 认证配置；
- 网络；
- 参数格式；
- 模型能力；
- 工具注册。

探针可以先把这些基础问题单独验证掉。

### 注意

SDK 探针证明“接得通”，不证明业务功能完整，也不替代端到端测试。

# 第三部分：软件工程概念

## 19. TDD：Red → Green → Refactor

### 三步

| 步骤 | 含义 |
|---|---|
| Red | 先写测试，确认它真的失败 |
| Green | 写最小实现，使当前测试通过 |
| Refactor | 在全绿保护下整理代码 |

### AI 项目为什么更需要 TDD

AI 系统常有：

- 模型输出不确定；
- 外部服务失败；
- 工具调用；
- 权限和审批；
- 多种异常分支。

TDD 能把这些行为变成明确、可重复的测试。

### 示例

AC-02：订单不存在时不得编造状态。

```text
Red：先写测试，当前实现会失败
Green：为 not_found 增加固定安全分支
Refactor：把错误映射抽成独立函数
```

### 关键规则

- 测试名包含 `AC-xx`；
- Red 阶段必须真的红；
- 不允许删断言、放宽断言或用 skip 假装通过；
- 每完成一个任务更新追溯矩阵。

---

## 20. 测试契约：让 Fake 和 Real 遵守同一接口

### 是什么

测试契约是组件之间关于输入、输出、错误和副作用的共同约定，并通过测试保证所有实现都遵守它。

### 示例

```ts
type OrderResult =
  | { ok: true; orderId: string; status: "pending" | "shipped" }
  | { ok: false; reason: "not_found" | "unauthorized" | "timeout" };
```

Fake 和 Real 都必须返回这个结构，而不能一个返回 `null`、另一个抛异常。

### 解决什么问题

防止出现：

```text
本地 Fake 测试全绿
真实服务返回格式不同
线上代码崩溃
```

### 与适配器的关系

适配器隐藏外部差异，测试契约规定适配器对 lib 暴露的稳定行为。

---

## 21. Web MVP：最小但完整的用户闭环

### 是什么

Web MVP 不是漂亮网站，而是能够被用户操作、看到成功结果、看到失败结果的最小 Web 产品。

```text
用户输入 → 系统处理 → 结果展示 → 错误或下一步
```

### 示例页面

订单查询助手至少可以有：

- 订单号输入框；
- 查询按钮；
- 加载状态；
- 结果区域；
- 未找到和服务异常提示；
- 高风险操作的确认区域。

### 为什么 Skill 强调页面

API 或脚本能运行，不代表用户路径成立。页面可以暴露：

- 输入不清楚；
- 错误不可理解；
- 输出过长；
- 审批步骤缺失；
- 用户不知道下一步。

---

## 22. lib / adapters / 外壳分层

### lib

放核心业务逻辑和规则：

- 不依赖页面；
- 不依赖具体 HTTP；
- 不依赖具体 LLM SDK；
- 容易用单元测试验证。

### adapters

对接外部依赖：

- LLM SDK；
- MCP；
- HTTP API；
- 文件系统；
- 浏览器存储；
- Fake 和 Real 实现。

### 外壳

用户和系统的入口：

- Web 页面；
- API 路由；
- CLI；
- 服务启动和环境配置。

### 推荐结构

```text
页面 / API / CLI
       ↓
      lib
       ↓
adapters
       ↓
LLM / MCP / 外部服务
```

### 分层的最大价值

同一个 `lib` 可以被：

- Web 页面调用；
- API 调用；
- CLI 调用；
- 单元测试调用。

替换模型或外部服务时，只需替换 adapter。

---

## 23. 拓扑 P / S / D / +CLI

> 这些字母是该 Skill 里的项目拓扑选项，不是所有行业都统一使用的固定缩写。

| 拓扑 | 含义 | 适合场景 |
|---|---|---|
| P | 纯前端，核心逻辑在浏览器 | 快速原型、无后端环境 |
| S | 同仓库前端 + API | 需要服务端保护配置或接外部服务 |
| D | 前后端分离 | 团队分工明确、系统边界更复杂 |
| +CLI | 在上述拓扑外增加命令行入口 | 批处理、自动化、研发流水线 |

### 选择时先问

1. 是否需要页面？
2. 是否需要保护密钥？
3. 是否需要服务端调用外部系统？
4. 是否有长任务或异步流程？
5. 是否需要批处理和自动化？

无论选哪种拓扑，都应尽量保持 `lib / adapters / 外壳` 分层不变。

---

## 24. CLI：命令行外壳

CLI 是另一种使用系统能力的入口，适合：

- 调试；
- 批处理；
- SDK 探针；
- Live Eval；
- CI 自动化。

示例：

```bash
app query-order --id A123
app eval --dataset samples.json
python scripts/ac_status.py requirements.md < vitest.json
```

CLI 不应重复实现核心业务逻辑，而应调用与 Web 共用的 `lib`。

---

## 25. CI 质量门禁

### 是什么

CI 质量门禁是在合并或交付前自动检查最低质量要求。

### 常见检查

```text
测试
→ 类型检查
→ lint
→ 构建
→ 契约测试
→ AC 状态
→ 必要的样本评估
```

### AI 项目的额外门禁

- Guardrail 测试必须通过；
- 高风险工具不能绕过审批；
- 关键 AC 必须有测试或 Live 证据；
- Live Eval 的失败场景必须有处理策略。

### 重要区别

“本地跑过测试”是一次操作；

“CI 质量门禁”是让不合格变更不能轻易继续流转的制度。

## 26. 脚手架与 Skill 复用

### 脚手架是什么

脚手架（Scaffold）是自动创建项目基础结构、依赖和配置的工具。

该 Skill 中的脚手架包括：

- `scaffold-next.sh`：Next.js + TypeScript + 测试基础；
- `scaffold-vite.sh`：Vite + React + TypeScript + 测试基础；
- `install.sh`：将 Skill 安装到 Claude Code 或 Kiro 项目。

### Skill 是什么

Skill 是可复用的专业工作方式，通常包含：

```text
触发条件
+ 流程说明
+ 参考规范
+ 模板
+ 脚本
+ 验证方法
+ 常见错误
```

### 两者区别

| 概念 | 主要复用对象 |
|---|---|
| 脚手架 | 代码目录、依赖、配置和项目骨架 |
| Skill | 工作流程、规范、模板、工具和经验 |

# 第四部分：易混淆概念

## 27. LLM、Agent、编排器

| 概念 | 本质 | 类比 |
|---|---|---|
| LLM | 语言理解与生成能力 | 大脑组件 |
| Agent | 围绕目标执行任务 | 办事员 |
| 编排器 | 协调步骤、状态和审批 | 项目经理 |

```text
LLM 可以没有 Agent。
Agent 通常使用 LLM。
复杂 Agent 流程通常需要编排器。
```

## 28. 工具调用与 MCP

```text
工具调用：我要调用 get_order_status。
MCP：这个工具如何被统一描述、发现和连接。
```

## 29. Fake、Real、Live

```text
Fake：验证逻辑。
Real：验证真实集成。
Live：验证真实条件下的完整使用路径。
```

## 30. EARS、AC、测试、Demo

```text
EARS：写清系统应该如何行为。
AC：定义什么叫完成。
测试：自动验证完成条件。
Demo / Live Eval：在接近真实的条件下展示证据。
```

## 31. Guardrail 与 HITL

```text
Guardrail：系统整体的安全边界。
HITL：在特定节点让人确认。
```

HITL 是 Guardrail 的一种方式，但输入校验、工具白名单和输出脱敏也属于 Guardrail。

## 32. 单元测试与测试契约

```text
单元测试：某段代码是否正确。
测试契约：多个实现之间的接口行为是否一致。
```

## 33. 脚手架与 Skill

```text
脚手架：快速搭项目。
Skill：快速采用一套成熟工作方式。
```

# 第七部分：初学者常见误区

## 误区 1：会调用 LLM 就等于会做 AI 开发

调用模型只是起点。还需要工具、规则、测试、权限、失败处理、评估和交付。

## 误区 2：Agent 越自主越好

自主程度应匹配风险、可逆性、权限和验证能力。

## 误区 3：Fake 全绿就能上线

Fake、Real、Live 分别验证不同层面，不能互相替代。

## 误区 4：所有业务规则都写进 Prompt

权限、金额、状态机、审批和不可违反的规则应优先放在可测试代码中。

## 误区 5：先做复杂页面

先完成一条最小用户路径：

```text
输入 → 处理 → 结果 → 失败提示
```

## 误区 6：把 Guardrail 当成敏感词过滤

真正的 Guardrail 还包括权限、工具白名单、参数校验、审批和停止条件。

## 误区 7：把 Skill 当成普通说明文档

Skill 应当包含流程、模板、脚本和验证方法，能够指导实际执行。
