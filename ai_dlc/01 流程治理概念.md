# 第一部分：流程治理概念

## 2. AI-DLC：AI Development Lifecycle

### 是什么

AI-DLC 是面向 AI 应用的开发生命周期。它把 AI 项目从“模型实验”变成一套可规划、可测试、可审批、可交付的工程流程。

### 文件中的位置

- `SKILL.md`：整体流程
- `stages/spec.md`：Inception
- `stages/tdd.md`：Construction
- `stages/demo.md`：收口与演示

### 解决什么问题

- 需求模糊，无法判断是否完成；
- 只证明模型能回答，没有证明系统可交付；
- 测试依赖真实服务，慢且不可复现；
- 模型有不确定性，却没有明确边界；
- 每个项目都重复搭建相同流程。

### 简单例子

“做一个订单查询助手”不能只写一个 Prompt，还要明确：

1. 用户可以提供什么输入；
2. 何时调用订单工具；
3. 订单不存在时如何回答；
4. 哪些字段不能泄露；
5. 退款等写操作是否需要人工审批；
6. 如何用测试和真实验证证明完成。

### 学习重点

先掌握完整链路：

```text
问题 → 需求 → AC → 测试 → 实现 → 真实验证 → 交付证据
```

## 3. Inception、Construction、收口

| 阶段 | 主要问题 | 典型产物 |
|---|---|---|
| Inception | 做什么、边界是什么、如何验收 | `questions.md`、`requirements.md`、`design.md`、`tasks.md` |
| Construction | 如何实现并证明每条需求 | 代码、测试、适配器、`traceability.md` |
| 收口 | 能否在目标条件下运行、如何演示 | `DEMO.md`、测试报告、Live Eval、复盘 |

### 与普通软件开发的对应关系

- Inception ≈ 需求分析与方案设计；
- Construction ≈ 开发、测试与集成；
- 收口 ≈ 验收、演示、发布准备。

### 为什么 AI 项目特别需要阶段化

AI 项目容易出现“先接模型、后补规则”的问题。阶段化要求先明确：

- 模型负责什么；
- 程序负责什么；
- 哪些动作必须经过人；
- 什么结果才算通过。

## 4. EARS：可验证的需求写法

### 是什么

EARS（Easy Approach to Requirements Syntax）把自然语言需求写成有触发条件、有主体、有可观察响应的句子。

### 五种基本句型

| 类型 | 句型 | 用途 |
|---|---|---|
| Ubiquitous | `THE 系统 SHALL 响应` | 永远成立的规则 |
| Event-driven | `WHEN 事件 THE 系统 SHALL 响应` | 用户操作或输入到达 |
| State-driven | `WHILE 状态 THE 系统 SHALL 响应` | 某种状态持续期间 |
| Unwanted | `IF 异常 THEN THE 系统 SHALL 响应` | 错误、缺失、违规 |
| Optional | `WHERE 特性存在 THE 系统 SHALL 响应` | 可选能力 |

### 示例

模糊需求：

```text
AI 应该智能地查询订单。
```

EARS 写法：

```text
WHEN 用户提供有效订单号 THE 订单助手 SHALL 调用订单查询工具。
IF 订单查询工具返回 not_found THEN THE 订单助手 SHALL 提示未找到订单且不得编造订单状态。
IF 用户未提供订单号 THEN THE 订单助手 SHALL 请求补充订单号。
```

### 合格判据

一条 EARS 最好满足：

- 只有一个主要 SHALL 响应；
- 能直接设计测试断言；
- 有具体字段、数字或枚举；
- 主体明确；
- 不把实现细节写进需求。

### 与其他概念的关系

```text
EARS → AC → 测试 → 实现 → Demo / Eval
```

## 5. AC：Acceptance Criteria，验收标准

### 是什么

AC 是判断一项需求是否完成的具体条件。它应该能得到明确的 PASS 或 FAIL。

### 示例

```text
AC-01：输入有效订单号时，系统返回订单状态。
AC-02：订单不存在时，系统提示未找到且不编造状态。
AC-03：订单服务超时时，系统给出失败提示。
AC-04：涉及修改订单的操作必须先经过确认。
```

### AC ID 的作用

Skill 要求使用稳定编号，例如 `AC-01`，并贯穿：

```text
requirements.md
→ tasks.md
→ 测试名称
→ 实现注释
→ traceability.md
→ DEMO.md
```

这样可以知道某条业务要求到底有没有被测试和实现。

### 优先级

- **P0**：演示或交付必须通过；
- **P1**：重要加料，时间不足时可暂缓；
- **P2**：后续增强。

## 6. 需求追溯：从需求追到代码和证据

### 是什么

需求追溯是建立以下对应关系：

```text
任务卡
  → EARS
  → AC
  → 任务
  → 测试
  → 实现
  → Demo / Live Eval
```

### 解决什么问题

- 需求变更后，知道哪些代码和测试受影响；
- 测试通过后，确认它确实覆盖了业务要求；
- Demo 不只是“演示好看的功能”，而是对应具体 AC；
- 出现问题时能追溯遗漏发生在哪一层。

### 典型表格

| AC | 测试 | 实现 | 证据 | 状态 |
|---|---|---|---|---|
| AC-01 | `test_ac_01_query_success` | `queryOrder()` | Demo-01 | PASS |
| AC-02 | `test_ac_02_not_found` | `handleNotFound()` | Demo-02 | PASS |

## 7. Human-in-the-loop：人工参与关键决策

### 是什么

Human-in-the-loop（HITL）指在 AI 流程的高风险节点，让人进行确认、修正、批准或终止。

### 适合人工介入的场景

- 修改外部数据；
- 删除、退款、转账、权限变更；
- 模型置信度低；
- 工具返回异常；
- 结果对用户影响重大；
- 操作不可逆。

### 示例

```text
用户请求退款
  → AI 识别意图
  → 查询订单是否满足退款条件
  → 生成退款草稿
  → 人工确认
  → 才允许调用退款工具
```

### 与 Guardrail 的关系

HITL 是 Guardrail 的一种实现方式，但 Guardrail 还包括：

- 输入校验；
- 工具白名单；
- 权限控制；
- 输出脱敏；
- 固定拒答；
- 失败时停止。

## 8. interactive 与 yolo

### interactive

交互式模式。AI 在关键节点停下来，让人查看计划、确认需求或批准操作。

适合：

- 需求不清；
- 高风险工具；
- 不可逆操作；
- 需要共同决策的项目。

### yolo

高自主执行模式。AI 在预先授权的范围内连续推进，减少逐步确认。

适合：

- 低风险；
- 可逆操作；
- 规则清楚；
- 重复性高；
- 已有充分测试和日志。

### 关键原则

```text
yolo ≠ 没有安全边界
```

即使自动模式，也应记录假设、尊重权限、遇到高风险操作时暂停。
