# 第三部分：软件工程概念

## 19. TDD：Red → Green → Refactor

### 三步

| 步骤 | 含义 |
|---|---|
| Red | 先写测试，确认它真的失败 |
| Green | 写最小实现，使当前测试通过 |
| Refactor | 在全绿保护下整理代码 |

### AI 项目为什么更需要 TDD

AI 系统常有：

- 模型输出不确定；
- 外部服务失败；
- 工具调用；
- 权限和审批；
- 多种异常分支。

TDD 能把这些行为变成明确、可重复的测试。

### 示例

AC-02：订单不存在时不得编造状态。

```text
Red：先写测试，当前实现会失败
Green：为 not_found 增加固定安全分支
Refactor：把错误映射抽成独立函数
```

### 关键规则

- 测试名包含 `AC-xx`；
- Red 阶段必须真的红；
- 不允许删断言、放宽断言或用 skip 假装通过；
- 每完成一个任务更新追溯矩阵。

## 20. 测试契约：让 Fake 和 Real 遵守同一接口

### 是什么

测试契约是组件之间关于输入、输出、错误和副作用的共同约定，并通过测试保证所有实现都遵守它。

### 示例

```ts
type OrderResult =
  | { ok: true; orderId: string; status: "pending" | "shipped" }
  | { ok: false; reason: "not_found" | "unauthorized" | "timeout" };
```

Fake 和 Real 都必须返回这个结构，而不能一个返回 `null`、另一个抛异常。

### 解决什么问题

防止出现：

```text
本地 Fake 测试全绿
真实服务返回格式不同
线上代码崩溃
```

### 与适配器的关系

适配器隐藏外部差异，测试契约规定适配器对 lib 暴露的稳定行为。

## 21. Web MVP：最小但完整的用户闭环

### 是什么

Web MVP 不是漂亮网站，而是能够被用户操作、看到成功结果、看到失败结果的最小 Web 产品。

```text
用户输入 → 系统处理 → 结果展示 → 错误或下一步
```

### 示例页面

订单查询助手至少可以有：

- 订单号输入框；
- 查询按钮；
- 加载状态；
- 结果区域；
- 未找到和服务异常提示；
- 高风险操作的确认区域。

### 为什么 Skill 强调页面

API 或脚本能运行，不代表用户路径成立。页面可以暴露：

- 输入不清楚；
- 错误不可理解；
- 输出过长；
- 审批步骤缺失；
- 用户不知道下一步。

## 22. lib / adapters / 外壳分层

### lib

放核心业务逻辑和规则：

- 不依赖页面；
- 不依赖具体 HTTP；
- 不依赖具体 LLM SDK；
- 容易用单元测试验证。

### adapters

对接外部依赖：

- LLM SDK；
- MCP；
- HTTP API；
- 文件系统；
- 浏览器存储；
- Fake 和 Real 实现。

### 外壳

用户和系统的入口：

- Web 页面；
- API 路由；
- CLI；
- 服务启动和环境配置。

### 推荐结构

```text
页面 / API / CLI
       ↓
      lib
       ↓
adapters
       ↓
LLM / MCP / 外部服务
```

### 分层的最大价值

同一个 `lib` 可以被：

- Web 页面调用；
- API 调用；
- CLI 调用；
- 单元测试调用。

替换模型或外部服务时，只需替换 adapter。

## 23. 拓扑 P / S / D / +CLI

> 这些字母是该 Skill 里的项目拓扑选项，不是所有行业都统一使用的固定缩写。

| 拓扑 | 含义 | 适合场景 |
|---|---|---|
| P | 纯前端，核心逻辑在浏览器 | 快速原型、无后端环境 |
| S | 同仓库前端 + API | 需要服务端保护配置或接外部服务 |
| D | 前后端分离 | 团队分工明确、系统边界更复杂 |
| +CLI | 在上述拓扑外增加命令行入口 | 批处理、自动化、研发流水线 |

### 选择时先问

1. 是否需要页面？
2. 是否需要保护密钥？
3. 是否需要服务端调用外部系统？
4. 是否有长任务或异步流程？
5. 是否需要批处理和自动化？

无论选哪种拓扑，都应尽量保持 `lib / adapters / 外壳` 分层不变。

## 24. CLI：命令行外壳

CLI 是另一种使用系统能力的入口，适合：

- 调试；
- 批处理；
- SDK 探针；
- Live Eval；
- CI 自动化。

示例：

```bash
app query-order --id A123
app eval --dataset samples.json
python scripts/ac_status.py requirements.md < vitest.json
```

CLI 不应重复实现核心业务逻辑，而应调用与 Web 共用的 `lib`。

## 25. CI 质量门禁

### 是什么

CI 质量门禁是在合并或交付前自动检查最低质量要求。

### 常见检查

```text
测试
→ 类型检查
→ lint
→ 构建
→ 契约测试
→ AC 状态
→ 必要的样本评估
```

### AI 项目的额外门禁

- Guardrail 测试必须通过；
- 高风险工具不能绕过审批；
- 关键 AC 必须有测试或 Live 证据；
- Live Eval 的失败场景必须有处理策略。

### 重要区别

“本地跑过测试”是一次操作；

“CI 质量门禁”是让不合格变更不能轻易继续流转的制度。

## 26. 脚手架与 Skill 复用

### 脚手架是什么

脚手架（Scaffold）是自动创建项目基础结构、依赖和配置的工具。

该 Skill 中的脚手架包括：

- `scaffold-next.sh`：Next.js + TypeScript + 测试基础；
- `scaffold-vite.sh`：Vite + React + TypeScript + 测试基础；
- `install.sh`：将 Skill 安装到 Claude Code 或 Kiro 项目。

### Skill 是什么

Skill 是可复用的专业工作方式，通常包含：

```text
触发条件
+ 流程说明
+ 参考规范
+ 模板
+ 脚本
+ 验证方法
+ 常见错误
```

### 两者区别

| 概念 | 主要复用对象 |
|---|---|
| 脚手架 | 代码目录、依赖、配置和项目骨架 |
| Skill | 工作流程、规范、模板、工具和经验 |
