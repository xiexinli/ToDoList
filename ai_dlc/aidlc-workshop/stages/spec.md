# 阶段 1：`aidlc spec`（Inception）

目标：从任务卡 + 客户材料出发，在一个**空仓库**里产出三份文件：`requirements.md`（含 EARS 验收清单）、`design.md`（含技术选型与从零脚手架命令）、`tasks.md`。上午 105 分钟内一个 3–4 人小组能完成。**只有两道门禁**：批准需求、批准设计与任务。

先读 `references/ears.md`、`references/questions.md`、`references/web-mvp.md`。

## Step 1 读材料，写理解摘要

- 读任务卡（最终产物 / 加料后任务 / 验收思路与标准 / 入口）和用户指定目录下的所有材料。
- 在 `questions.md` 开头写 `## 0. 理解摘要`（≤ 20 行）：要做什么、输入、输出、已知规则、材料里**缺什么**、业务语言（用户侧文本用什么语言）。
- 不要在这一步开始写需求。

## Step 2 澄清问题（两组）

写入 `questions.md`，格式见 `references/questions.md`（A–E 选项 + `X. Other (please specify)` + "若不回答我将假设" + 空 `[Answer]:`）。

**A 组：业务澄清（3–6 题）**。只问影响 EARS 怎么写或任务怎么拆的问题；材料里已有答案的不要问，直接进假设。

**B 组：技术确认（固定 5 题，每次都问，这是 AI-DLC 里"让客户确认技术细节"的环节）**。每题给推荐项和一句取舍理由，客户拍板：
1. 技术栈与框架（选项见 `web-mvp.md` §3）
2. 测试框架与运行命令
3. **拓扑**与页面形态：纯前端 / 同仓库前端+API / 前后端分离 / 加 CLI（见 `web-mvp.md` §2，按现场条件选）；哪几个页面、什么控件
4. 存储：服务端文件目录和/或浏览器存储（localStorage / IndexedDB / 下载）；确认不上云、无数据库
5. 外部依赖策略：哪些用 mock/fake（接口、LLM）、LLM 从服务端还是浏览器直连（本机 AKSK 仅演示）、是否允许 live 抽样、凭证从哪来；运行时版本与包管理器

硬约束（不问，直接写进 requirements §6）：核心逻辑 lib 与外壳分离、外部依赖走适配器、不上云不建库、有可操作页面（`web-mvp.md` §0）。

- interactive：把两组问题（含默认假设）列给人，停下等回答；回答写回文件；模糊回答追问一轮。**所有 `[Answer]:` 填满前不得进入 Step 3。** 人说"都按默认/推荐"也算填满。
- yolo：用"若不回答我将假设"作答，`[Answer]: B（自动）`，继续。

## Step 3 写 requirements.md（用 `templates/requirements.md`）

必须包含：
1. **背景与目标**（3–5 行）。
2. **范围**：范围内 / 范围外（明确写出今天不做的；MVP 边界见 web-mvp.md §5）。
3. **术语**。
4. **任务卡验收 → EARS 覆盖表**：任务卡"验收思路与标准"每一句一行，右列列出覆盖它的 `AC-xx`。**不允许有未被覆盖的验收句**。
5. **EARS 验收清单**：表格列 = `ID | 类型 | 优先级 | EARS 语句 | 测试思路（一句话）`。
   - 数量 **8–20 条**；**P0 目标 ≤ 10、硬上限 12**（P0 = 演示必须过）。超了按 `references/ears.md` 的"P0 降级规则"降，"红线"条目可标 `P0!` 不降。
   - 每条一个可观测响应；"同一张数据表 / 同一个函数一次断言能覆盖"的可合并为一条。写不出"测试思路"的条目要拆或删。
   - 类型覆盖：至少各 1 条 Event-driven、Unwanted；加料用 WHERE。
   - 语句格式：中文描述 + 英文关键字大写。
6. **非功能与约束**：把 B 组技术确认的答案落成约束（栈、运行命令、存储位置、mock/live 策略、运行时版本）。
7. **假设**：只写 `Q1 → B：一句话` 的引用形式；yolo 新增的假设标"自动"。
8. **开放问题**（留给客户）。

## 门禁 1：批准需求

- 贴出：两组答案汇总（bullet）+ EARS 清单（ID / 优先级 / 语句）+ 覆盖表 + "降了哪几条 P0、为什么"。问："以上理解与验收标准是否批准？"（`Approve` / `Request changes`）。
- interactive 停下等；改完再贴再问。yolo 记录后继续。
- 批准后 **AC ID 冻结**：后续只能新增 `AC-xx`（顺延编号）或标 `废弃`，不得改号。

## Step 4 写 design.md（用 `templates/design.md`）

- **架构**：按 `references/web-mvp.md` §1 的分层写组件表（层 / 模块 / 职责 / 输入输出 / 对应 AC）：lib 列函数签名；adapters 列 real/fake 两套；外壳按 T3 选的拓扑列——页面列有哪些、各放什么控件；有 API 的列路径、方法、请求/响应 JSON；有 CLI 的列参数。
- **存储**：按 T4 的答案写——服务端文件（目录、命名、环境变量如 `DATA_DIR`）和/或浏览器存储（localStorage/IndexedDB 的 key、下载文件名）。
- **关键流程**：主流程 + 1–2 个异常流程（对应 Unwanted 条目）。
- **测试策略**：`AC 范围 | 层次（lib 单元 / API 契约 / 端到端 / live）| fake/fixture/样本`。外部依赖一律抽象成接口并提供 fake；列出要自造的样本清单。
- **Agent 类课题**额外写 `design-agent.md`（用 `templates/design-agent.md`）。
- **技术选型、从零脚手架命令与 SDK 探针**：写出 T0 要**逐条执行**的命令（如 `npx create-next-app@latest . --ts --app --src-dir --yes`、`npm i -D vitest`、`npm i xlsx jszip`），测试/类型检查/lint 命令，关键 SDK 版本，探针要做的最小调用。这一节是 T0 的执行脚本，要能照抄。

## Step 5 写 tasks.md（用 `templates/tasks.md`）

规则：
- **T0 从零脚手架**（0.5–1h）：按 design.md 的命令生成项目、装测试框架、smoke 测试通过、SDK 探针通过、dev 页面能打开、类型检查与 lint 通过。网络慢时可用导师的兜底脚手架，但要在 DEMO 复盘里写明。
- 任务按分层从内到外排：先 lib（大部分 AC），再外壳契约（有 API/CLI 时），最后页面接线。页面不要拆太碎，一个"页面打通"任务即可。
- 每个任务 **1–4 小时**（agent 小时），有 `依赖`、`覆盖 AC`、`完成定义 = 覆盖 AC 的测试全部通过 + 类型检查/lint 通过`。
- 按 P0 → P1 → P2 排序；≥ 4 个任务时有 **集成检查点任务**（起 dev/preview 服务，真实入口跑主流程 + 1 个异常流程；见 tdd.md）。
- 倒数第二个任务是 **页面打通**（页面 ↔ lib 或 API 接线、localStorage），最后一个是 **集成检查点 + 演示**（真实入口走主流程与异常流、DEMO.md、演示输入样例）。纯前端拓扑下集成检查点就是浏览器冒烟，所以页面必须先接好。**页面任务不可跳过**：没有页面就不是 MVP。
- 标出"时间不够可跳过"的任务（只含 P1/P2）。
- 每条 `AC-xx` 至少出现在一个任务里；`AC → 任务` 反查表由你生成并自检，人不用维护。

## 门禁 2：批准设计与任务

- 贴出：组件表、T0 脚手架命令、任务列表（ID / 标题 / 估时 / 覆盖 AC / 可跳过）、总估时。问是否批准开始 TDD。
- 阶段结束输出：三份文件路径、EARS 总数与 P0 数、任务总数与总估时；yolo 下把"若交互我会问的问题"追加到 `questions.md` 末尾小节；打卡 timeline.md。
