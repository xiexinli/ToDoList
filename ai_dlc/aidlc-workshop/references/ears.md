# EARS 验收标准写法

EARS（Easy Approach to Requirements Syntax）用五种固定句型把需求写成"一个触发/状态 → 一个主体 → 一个可观测响应"。本 workshop 约定：**中文描述 + 英文关键字大写**。

## 五种句型

| 类型 | 句型 | 什么时候用 |
|---|---|---|
| Ubiquitous | THE `<系统>` SHALL `<响应>` | 永远成立的规则、格式约束 |
| Event-driven | WHEN `<触发事件>` THE `<系统>` SHALL `<响应>` | 输入到达、用户操作、文件出现 |
| State-driven | WHILE `<状态>` THE `<系统>` SHALL `<响应>` | 处于某模式/某端/某配置期间 |
| Unwanted | IF `<不期望条件>` THEN THE `<系统>` SHALL `<响应>` | 错误、缺失、违规、异常 |
| Optional | WHERE `<可选特性存在>` THE `<系统>` SHALL `<响应>` | 加料功能、可开关的能力 |

可以组合：`WHILE 目标端为 Android, WHEN 读取到含 ' 的译文, THE 生成器 SHALL …`。

## 一条合格 EARS 的判据

1. **单一响应**：一个 SHALL，一个可观测结果。出现"并且/以及"两个结果就拆两条。
2. **可断言**：能在 1 分钟内想出测试的 `assert`。写不出就改写或删。
3. **具体**：有数字/枚举/文件名/字段名，不用"正确""合理""友好"这类词。
4. **主体明确**：`<系统>` 是你要做的那个组件（生成器 / 客服 Agent / MCP 工具），不是"用户"。
5. **不含实现细节**：写"报告中列出 (key, lang)"而不是"用 pandas 过滤空值"。

## 反例 → 改写

| 反例 | 问题 | 改写 |
|---|---|---|
| 系统应正确生成多语文件 | "正确"不可测 | THE 生成器 SHALL 为每个目标端、每个目标语言各生成一个文件，且文件能被该端的解析器无错解析 |
| 缺翻译时应友好提示 | 响应不可观测 | IF 某行某语言译文为空 THEN THE 生成器 SHALL 在报告中列出 `(key, lang)` 并将退出码设为 2 |
| 客服机器人不能泄露敏感信息并转人工 | 两个响应 | ① IF 用户消息中包含密码或验证码 THEN THE Agent SHALL 回复安全提示且不把该内容写入任何工具调用 ② WHEN 用户消息包含 "human agent" THE Agent SHALL 在本回合回复转人工并停止调用工具 |

## 任务卡验收 → EARS 改写示例（课题 A）

（以下 AC 编号与优先级仅为示例，不占用你的编号，也不代表你的课题必须有这些条目。）

任务卡原句："目标端所需 key 零缺失"

```
AC-03 | Ubiquitous   | P0 | THE 生成器 SHALL 使 PRD 中每一行在每个目标端的每个目标语言文件中恰好出现一次 key
AC-04 | Unwanted     | P0 | IF 某目标语言在 PRD 中没有对应列 THEN THE 生成器 SHALL 按语言映射表回退（如 iOS ga/zh-HK 用 en），并在报告中标注 "fallback"
AC-05 | Event-driven | P1 | WHEN 生成完成 THE 生成器 SHALL 输出一份 key 覆盖矩阵（端 × 语言 × 缺失数），缺失为 0 时退出码为 0
```

任务卡原句："与基线 diff 符合预期"

```
AC-09 | Optional | P1 | WHERE 用户提供了基线目录 THE 生成器 SHALL 输出 diff 报告，且基线中已有的 key 与 value 全部保持不变
AC-10 | Unwanted | P1 | IF 新 key 已存在于基线且 value 不同 THEN THE 生成器 SHALL 不覆盖，并在报告中列为 "conflict" 等待人工确认
```

## 合并判据（避免条目碎成 30 条）

"单一响应"不等于"单一断言"。以下情况合并为一条：
- 同一张对照表/枚举表的多行（如语言码映射 kr→ko、jp→ja、se→sv 是一条 AC，一个参数化测试）。
- 同一个函数、同一次调用就能一次断言完的多个字段（如接口成功返回的 `code`/`data`/`msg` 三个字段）。

以下情况必须拆：触发条件不同（正常 vs 缺参 vs 查不到）、目标端不同（iOS 与 Android 的转义规则）、响应类型不同（写文件 vs 写报告 vs 退出码）。

## 优先级与 P0 降级规则

- **P0**：演示必须过；没有它 demo 不成立。
- **P1**：加料，体现方法论"全貌"；时间不够可跳过。
- **P2**：会后跟进。

一天的量：8–20 条，**P0 目标 ≤ 10，硬上限 12**。"做错会出事故"的条目（如占位符转换错、转义错导致线上崩、守则被绕过）可标 `P0!`（红线）不参与降级，但红线也算在 12 以内，且**最多 3 条**——超过 3 条说明你在用红线躲降级。第一版 P0 超过目标时按下面顺序降级为 P1（先保住的排前面）：
1. 保：外部契约（文件格式 / 接口返回结构 / MCP 工具契约）。
2. 保：业务红线（SOP 守则、禁译词、不覆盖基线这类"做错会出事"的）。
3. 保：主流程闭环 1 条 + 最典型的异常流 1–2 条。
4. 降：重试次数、语言/格式美化、覆盖报告、子集参数、摘要输出。
5. 降：追问 / 缺信息处理——**除非**客户样例里这类对话占多数（如客服课题 9 条样例里 4 条是"信息不全需追问"），那它就是主流程的一部分，留在 P0。
6. 降：所有 WHERE 条目。

降级是你的提议，不是决定：interactive 下在门禁 1 把"降了哪几条、为什么"单独列出来请人确认；yolo 下写进 requirements 的假设小节。
