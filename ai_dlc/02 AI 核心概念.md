# 第二部分：AI 核心概念

## 9. LLM：大语言模型

### 是什么

LLM（Large Language Model）是理解和生成自然语言的模型。它擅长：

- 问答；
- 总结；
- 分类；
- 信息抽取；
- 意图识别；
- 生成结构化输出；
- 规划工具调用。

### 不是什么

LLM 不是：

- 可靠数据库；
- 权限系统；
- 业务规则引擎；
- 自动正确的事实来源。

### 示例

用户输入：

```text
我的订单 A123 怎么还没到？
```

LLM 可以识别：

```json
{
  "intent": "query_order_status",
  "order_id": "A123"
}
```

但是否真的查询订单，应由程序和工具完成。

### 学习重点

把 LLM 当作“概率型语言组件”，不要把它当成完全确定性的函数。需要给它配合：

- 结构化输入输出；
- 工具；
- Guardrail；
- 测试；
- 失败和超时处理。

## 10. Agent：智能体

### 是什么

Agent 是以 LLM 为核心、能够理解目标、选择步骤、调用工具、读取结果并继续完成任务的系统单元。

一个 Agent 通常包含：

```text
目标 + 上下文 + LLM + 工具 + 状态 + 规则 + 停止条件
```

### LLM 与 Agent 的区别

| 概念 | 主要能力 |
|---|---|
| LLM | 理解和生成文本 |
| Agent | 围绕目标完成多步任务 |

LLM 可以没有工具；Agent 通常需要工具、状态和执行规则。

### 示例

```text
用户：查询 A123，并告诉我是否需要联系客服

Agent：
1. 识别订单号和意图；
2. 调用订单工具；
3. 读取物流结果；
4. 判断是否异常；
5. 生成解释和建议。
```

### 初学建议

不要从“万能 Agent”开始。先做：

```text
一个目标 → 一个只读工具 → 一个结构化结果
```

## 11. 工具调用：让模型从“会说”变成“能做”

### 是什么

工具调用（Tool Calling / Function Calling）是模型输出结构化调用请求，由程序真正执行工具，再把结果交回模型。

### 基本流程

```text
用户问题
  → LLM 判断需要工具
  → 输出工具名和参数
  → 程序校验参数并执行
  → 工具返回结果
  → LLM 组织最终回答
```

### 示例

模型请求：

```json
{
  "tool": "get_order_status",
  "arguments": { "order_id": "A123" }
}
```

工具返回：

```json
{
  "ok": true,
  "order_id": "A123",
  "status": "shipped"
}
```

### 工具设计原则

1. 参数少且明确；
2. 输入输出结构化；
3. 成功与失败格式稳定；
4. 只读与写操作分开；
5. 权限判断不能只交给模型；
6. 每个工具都有 Fake 和契约测试。

## 12. MCP：Model Context Protocol

### 是什么

MCP 是一种标准化接入模型上下文、工具和外部资源的协议思路。

可以简单理解为：

```text
工具调用 = 具体调用某个能力
MCP = 以统一方式描述、发现和连接这些能力
```

### 它解决的问题

没有统一接入方式时，不同模型、客户端和业务系统之间会出现大量重复集成代码。MCP 的目标是让工具和上下文更容易复用。

### 工具调用与 MCP 的区别

| 概念 | 关注点 |
|---|---|
| 工具调用 | 模型如何请求执行某个动作 |
| MCP | 工具、资源和上下文如何标准化暴露和接入 |

### 学习顺序

1. 先写本地函数工具；
2. 设计清楚输入、输出、错误和权限；
3. 写 Fake 和契约测试；
4. 再学习如何用 MCP 暴露工具。

## 13. 编排器：协调 Agent、工具和流程

### 是什么

编排器（Orchestrator）负责安排任务顺序、管理状态、处理失败、决定何时调用工具、何时暂停审批以及何时结束流程。

### 示例

```text
校验输入
  → 查询订单
  → 判断业务规则
  → 生成建议
  → 请求人工审批
  → 执行写操作
  → 记录结果
```

### Agent 与编排器的区别

| 概念 | 类比 |
|---|---|
| Agent | 负责完成一项智能任务的执行者 |
| 编排器 | 负责分配步骤和控制全局流程的协调者 |

### 设计建议

确定性流程优先写在程序中：

```text
校验 → 查询 → 判断 → 审批 → 执行 → 记录
```

只把适合语言理解、总结、分类和生成的部分交给 LLM。

## 14. Guardrail：AI 系统的护栏

### 是什么

Guardrail 是限制 AI 输入、输出、工具和行动范围的规则与机制。

### 四类 Guardrail

| 类型 | 示例 |
|---|---|
| 输入护栏 | 缺少必要参数时追问；检测敏感信息 |
| 模型护栏 | 输出必须符合 JSON 或固定格式 |
| 工具护栏 | 工具白名单、参数范围、权限校验 |
| 流程护栏 | 写操作必须审批；失败后停止 |

### 示例

```text
IF 工具返回 not_found
THEN 系统 SHALL 说明未找到，且不得推测具体状态。
```

### 重要原则

不要只靠 Prompt 保护高风险操作。权限、金额计算、审批和状态变更等确定性规则应放在可测试代码中。

## 15. Fake、Real、Live：真实性逐步提升

| 层级 | 用途 | 优点 | 风险 |
|---|---|---|---|
| Fake | 单元测试和离线演示 | 快、稳定、可重复 | 可能与真实实现不同 |
| Real | 真实 SDK 或受控测试环境 | 验证集成、协议和配置 | 环境复杂、不稳定 |
| Live | 接近真实用户和目标环境 | 验证整体可用性 | 成本、权限和副作用较高 |

### 示例

```text
Fake：固定返回 shipped
Real：调用测试环境订单服务
Live：在授权条件下走完整真实用户路径
```

### 重要区别

```text
Fake 通过 ≠ Real 通过
Real 通过 ≠ Live 已验证
Live 可用 ≠ 可以取消 Guardrail
```

### 推荐顺序

```text
Fake 测试
  → Real 集成验证
  → 受控 Live 验证
  → 扩大发布范围
```

## 16. 合成样本：可控、可重复的测试数据

### 是什么

合成样本（Synthetic Samples）是人工设计或程序生成的测试输入、工具返回、对话和边界数据。

### 为什么需要

真实数据可能：

- 包含隐私；
- 难以覆盖罕见错误；
- 不稳定；
- 获取成本高；
- 不适合频繁跑 CI。

### 示例

```json
{
  "name": "订单不存在",
  "input": "查询 X999",
  "tool_result": { "error": "not_found" },
  "expected": "提示未找到，不得编造状态"
}
```

### 设计方法

每条 AC 至少设计：

1. 一个正常样本；
2. 一个边界样本；
3. 一个异常样本。

## 17. Live Eval：真实条件下的 AI 评估

### 是什么

Live Eval 是在真实模型、真实 SDK、真实或接近真实的外部服务和真实运行条件下，对 AI 系统进行评估。

### 不只看回答文本

还应检查：

- 是否调用正确工具；
- 工具参数是否正确；
- 是否遵守 Guardrail；
- 是否在失败时安全降级；
- 是否出现幻觉或虚假承诺；
- 是否满足 AC。

### 评估记录示例

```markdown
场景：订单不存在
输入：查询 X999
实际工具调用：get_order_status({id: "X999"})
实际结果：not_found
是否满足 AC-02：是
是否触发护栏：是
问题：无
```

### 与普通单元测试的区别

- 单元测试追求快、稳定、可重复；
- Live Eval 追求接近真实，允许存在环境波动；
- Live Eval 不应替代单元测试。

## 18. SDK 探针：先验证依赖，再开发复杂功能

### 是什么

SDK Probe 是一个极小的验证程序，用于确认 SDK、认证、网络、工具协议或模型调用是否真的可用。

### 探针通常做什么

```text
加载配置
  → 发送最小请求
  → 检查返回
  → 输出版本、耗时和错误类型
```

### 解决什么问题

当复杂 Agent 失败时，问题可能来自：

- SDK 版本；
- 认证配置；
- 网络；
- 参数格式；
- 模型能力；
- 工具注册。

探针可以先把这些基础问题单独验证掉。

### 注意

SDK 探针证明“接得通”，不证明业务功能完整，也不替代端到端测试。
